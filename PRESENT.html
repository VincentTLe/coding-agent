The ReAct Loop — How It Thinks and Acts

REASON
think
ACT
call tool
OBSERVE
read result
REPEAT
loop
for _ in range(max_iters):     # safety net
    msg = model.chat(messages, tools)
    messages.append(msg)          # memory!
    if not msg.tool_calls:       # done
        return msg.content
    for call in msg.tool_calls:
        r = run_tool(call.name, call.args)
        messages.append({"role":"tool",
          "tool_call_id": call.id,
          "content": r})
  • Model is a STATELESS API — the messages list IS the memory; whole convo re-sent each turn
  • Each result returns as role=tool, paired by tool_call_id
  • max_iters cap = safety net; agent ends only by calling finish
This is the engine. Four steps in a loop: reason, act, observe, repeat. I send the model the conversation so far plus the JSON schemas for my tools. It either returns plain text — meaning it thinks it's done — or it returns tool calls. I execute each tool and append the result back as a message with role 'tool.' Then I loop. The single most important idea: the model is STATELESS. The vLLM server remembers nothing between calls. So this messages list — this growing Python list — IS the memory. Every turn I re-send the entire conversation; that's how it 'remembers' what it read and did. Each result carries a tool_call_id so the model knows which call this answer belongs to, since it can fire several at once. And there's a hard max_iters cap, so a confused agent can never spin forever. This is the part I most wanted to build myself — because if a framework hides it, I can't study it.

Eleven tools, grouped into five families — I won't read them all, the grouping is the point. File I/O to read and edit code. Discovery to navigate a repo. Execution — bash and Python — to actually run things. Delegation, where the agent can spawn a focused sub-agent. And finish, which is how the agent ends a session — importantly, just replying in prose does NOT end it; remember that, it comes back in two slides. The design idea that keeps this clean: each tool is a function plus a JSON schema in an append-only registry, so adding a tool never touches the loop. The load-bearing safety piece is the sandbox: every file path goes through one function, _safe_path, which resolves the path and rejects anything that escapes the workspace — a real path-traversal defense, CWE-22. And tools never raise an exception that kills the loop; a bad call comes back as an 'ERROR' string the model reads as feedback and retries.

The Real Failure Mode: It Talked Instead of Acting

Before — talk, don't act

[assistant] "Here is the fix: def solve(n): return n*2 That should resolve it." ↳ no tool call → loop exits ✗ FAIL (no_action)

After — guardrail nudges

[guardrail] you replied with text but nothing changed on disk — call a tool now. → write_file("solve.py", ...) → run_bash("pytest -q") ✗ FAIL
  • From the eval traces, the dominant failure wasn't bad CODE — the model replied in PROSE without calling a tool → loop thinks it's done → task fails (no_action: 66/627)
  • Fix: a guardrail that detects "said something, did nothing" and nudges it to act (up to 2 nudges) — recovered most. A tool-use fix, not a smarter model. My genuine contribution.
When I actually read the eval traces — which I could only do because the agent logs every step — I found the dominant failure wasn't bad code. It was the model replying in prose: it would describe the function, even write the code as text in its message, but never call write_file. The loop, by its own contract, sees 'no tool call' and assumes it's done — so the task fails even though the model 'knew' the answer. That's the no_action failure: 66 times out of 627. The fix isn't a bigger model — it's a guardrail. When the agent stops without ever having called a tool, I nudge it: 'you replied with text but nothing changed on disk, call a tool now.' Up to two nudges, then it gives up cleanly. That recovered most of those cases. This is the part I'd call my genuine empirical contribution: the win came from diagnosing a tool-use behavior in the traces, not from swapping in a smarter model. You can only find this if you can see it.

🔒 weights FROZEN — the network never changes
  • Improve the agent by editing a natural-language SKILL document — never touching model weights
  • Validation gate: a candidate edit is kept only if it scores strictly higher on a val split (ties rejected) + a protected slow-update region
  • Think of it as gradient descent on TEXT — the prompt learns, the network doesn't
Here's the research-flavored angle, SkillOpt. The question: can I make the agent better without fine-tuning — without ever touching the model's weights? The idea is to optimize a natural-language SKILL document that gets appended to the system prompt. The loop mirrors training: I roll the agent out on a train split, the optimizer reflects on the failures and successes, and proposes edits to the skill — append, insert, replace, delete. Then the key part, a validation GATE: a candidate edit is only accepted if it scores strictly higher on a held-out val split; ties are rejected. There's also a protected 'slow-update' region for durable strategy that updates only at epoch boundaries. So it's gradient-descent-shaped, but the gradient is on TEXT and the network is frozen. It's a clean substrate — and it forced me to be very careful about measurement, which is the next slide.

  • 3-arm test on 84 held-out tasks: empty 0.786 / seed 0.738 / optimized 0.774
  • Exact-binomial McNemar: opt vs empty p=1.000, opt vs seed p=0.453 (all p≥0.29)
  • Re-running the same config flipped ~6/84 tasks (vLLM nondeterminism at temp=0) — deltas = noise
  • Reported with Wilson CI + exact McNemar + noise-floor heuristic. Honest stats > a cherry-picked win.
INCONCLUSIVE
And here's where honesty matters more than a headline. On a held-out 84-task test split, three arms: the empty skill scores 0.786, the seed skill 0.738, the optimized skill 0.774. So the optimized version sits between — it does not clearly help. I ran exact-binomial McNemar tests on the paired outcomes: optimized versus empty, p equals 1.000; optimized versus seed, p equals 0.453; nothing reached p below 0.05, everything was 0.29 or higher. Worse — and this is the honest killer — when I re-ran the exact same config, about 6 of 84 tasks flipped purely from vLLM's nondeterminism at temperature zero. So the differences between arms are the SAME SIZE as the run-to-run noise. The verdict is INCONCLUSIVE, under-powered. I report it with Wilson confidence intervals, exact McNemar, and a noise-floor heuristic. I want to be clear: the contribution here is the methodology — measuring it honestly enough to KNOW it's inconclusive — not a positive result I don't have.

Let me be straight about the limits, because overclaiming would undo the whole point of this talk. On capability: 67.3 percent is solid for toy-to-moderate tasks, but the hard hand-written set is only 21.6 — this is not SWE-bench-grade repository surgery. Engineering: there's no real tool parallelism, tools run one at a time, and there's a single shared workspace, so I don't isolate concurrent tasks. The backend is stochastic — the same task can pass one run and fail the next, even at temperature zero, because of vLLM nondeterminism; that's the same noise that made SkillOpt inconclusive. And SkillOpt itself is under-powered — I have no significant result. Finally, the ReAct loop is a faithful reimplementation, not a new algorithm. None of these are excuses; they're the honest boundary of what I can defend.
