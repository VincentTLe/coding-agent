SECTION 1 — PROTOCOL FOUNDATIONS

OpenAI Chat Completions API

sequenceDiagram

Next call resends ALL messages

The API is a single HTTP route: POST /v1/chat/completions. You send a JSON body with the entire conversation history, the server replies with the model's next message, and that's the whole protocol. The server is stateless — it has no memory between calls. Your Python list of messages IS the memory.

Why stateless? Total control. You can trim old turns, fork conversations, swap models mid-session, replay verbatim. The Assistants API holds state server-side, but you lose all of that for vendor convenience.

The 4 roles

RoleWhoSpecial fields
systemRules / persona—
userThe human—
assistantModel's replytool_calls
toolTool execution resulttool_call_id (required!)

finish_reason values

  • "stop" — natural EOS or stop sequence hit
  • "length" — max_tokens truncated the output
  • "tool_calls" — model wants to call tools, see message.tool_calls
  • "content_filter" — safety filter blocked
In examples/01_chat.py the entire pattern fits in ~20 lines: 
messages = [{"role": "system", "content": "..."}]
while True:
    user_input = input("[you] ")
    messages.append({"role": "user", "content": user_input})
    resp = client.chat.completions.create(model=MODEL, messages=messages)
    msg = resp.choices[0].message
    messages.append({"role": "assistant", "content": msg.content})
Memory = the Python list. Server never holds state.

Streaming + Server-Sent Events

Streaming exists to reduce perceived latency. A 500-token reply blocks for ~10s; streamed, the first character appears in ~200ms and scrolls smoothly while still generating. The transport is plain HTTP with Content-Type: text/event-stream — chunks framed as data: {...}\n\n, terminated by data: [DONE]\n\n.

The 3 delta fields you must accumulate

  • delta.content — visible text. Just string-concat.
  • delta.reasoning_content (or delta.reasoning) — model's hidden thinking, vendor extension via vLLM's reasoning parser.
  • delta.tool_calls — tricky. One tool call spreads across MANY deltas. JSON arguments arrive chunked. Multiple parallel calls interleave by index.
The tool_calls fragments arrive split: id + function.name in the first delta of an index, then function.arguments dribbles in across many deltas. You accumulate by index in a dict.
In cli/chat.py:163-174 — the accumulator pattern: 
if delta.tool_calls:
    for tcd in delta.tool_calls:
        idx = tcd.index
        if idx not in tool_calls:
            tool_calls[idx] = {"id": "", "name": "", "arguments": ""}
        if tcd.id:
            tool_calls[idx]["id"] += tcd.id
        if tcd.function:
            if tcd.function.name:
                tool_calls[idx]["name"] += tcd.function.name
            if tcd.function.arguments:
                tool_calls[idx]["arguments"] += tcd.function.arguments

The streaming print primitive

# end="" prevents newline between fragments
# flush=True forces immediate write() syscall
print(chunk, end="", flush=True)

Without flush=True, Python buffers stdout and you lose the streaming effect. Without end="", every chunk gets a newline.

An LLM is text-in/text-out. To "call Python functions," we need a contract: JSON Schema (Draft 2020-12) declares what tools exist; the model emits a structured tool_calls request; we execute and return results as role:"tool" messages. OpenAI invented this in 2023; everyone (Anthropic, vLLM, Ollama, Mistral) copies it verbatim.

Anatomy of a tool schema

{
  "type": "function",
  "function": {
    "name": "read_file",
    "description": "Read full contents of a text file.",
    "parameters": {
      "type": "object",
      "properties": {
        "path": {"type": "string", "description": "Relative path."}
      },
      "required": ["path"]
    }
  }
}
The description field is part of the prompt. The model reads it during planning. "Use only for read-only inspection" actually changes behavior. Write descriptions like you're writing a prompt.

The 5 common pitfalls

  1. Malformed JSON in arguments (Python triple-quotes, unescaped newlines)
  2. Hallucinated tool names (model invents edit_file)
  3. Unwanted tool calls (model calls run_bash("ls") to answer "hi")
  4. Forgetting tool_call_id → API 400s
  5. Treating arguments as dict — it's a STRING of JSON, you must json.loads()
Our dispatcher in src/tools.py:217 converts every failure into an error STRING the model can read on the next turn — never raises: 
def execute_tool(name: str, arguments_json: str) -> str:
    if name not in TOOLS:
        return f"ERROR: unknown tool {name}. Available: {list(TOOLS)}"
    try:
        args = json.loads(arguments_json) if arguments_json else {}
    except json.JSONDecodeError as e:
        return f"ERROR: bad JSON arguments: {e}"
    try:
        result = TOOLS[name](**args)
    except TypeError as e:
        return f"ERROR: bad args for {name}: {e}"
    except Exception as e:
        return f"ERROR: {name} crashed: {e}"
    return result
This single function addresses pitfalls 1-4 by giving the model recoverable error feedback.

The agent started with 3 tools (read_file, write_file, run_bash) — the bare minimum to inspect, edit, and verify code. It now ships 10 tools in four families. Every tool is still a plain Python function in src/tools.py registered in the TOOLS dict and exposed to the model via a JSON Schema; the dispatcher and sandbox from Section 3 are unchanged. More tools just means a richer action space for the same ReAct loop.

The full belt

FamilyToolWhat it does
File I/Oread_fileRead full contents of a text file.
write_fileCreate or overwrite a file with new contents.
apply_patchSurgical edit — replace old_text with new_text; old_text must match exactly once or it refuses.
multi_editApply several edits to one file atomically — all succeed or none are written.
Discoverylist_dirList entries in a directory.
glob_filesFind files by glob pattern (e.g. **/*.py).
grep_filesSearch file contents by regex across the workspace.
Executionrun_bashRun a shell command, CWD pinned to the workspace.
run_pythonRun a Python snippet / script in the workspace.
Delegationspawn_subagentLaunch a child agent in a subprocess with its own context window (timeout 300s, max_iters 8) and collect its final answer.
Why apply_patch over write_file? Rewriting a 400-line file to change one line costs ~400 lines of output tokens every edit. A patch sends only the changed span. The exactly-once match rule is the safety mechanism: if old_text is ambiguous (matches 0 or 2+ places) the tool refuses rather than edit the wrong spot, and the model gets an error string it can recover from — same recoverable-error discipline as the Section 3 dispatcher.
Why multi_edit is atomic. Several edits to the same file are validated together and written in one shot. If edit #3 of 5 fails to match, nothing is written — the file never lands in a half-edited state that would corrupt the next read.
spawn_subagent = divide and conquer. The parent delegates a self-contained subtask (e.g. "find every caller of foo()") to a fresh agent running as a subprocess. The child has its own clean context window, runs up to max_iters 8 turns or 300s, and returns just its final answer — so the parent's context only absorbs the conclusion, not the child's entire exploration. This is the same isolation pattern Claude Code uses for its sub-agents.
Every tool is registered in the TOOLS dict in src/tools.py and dispatched by the same execute_tool() shown in Section 3 — adding a tool is: write the function, add a schema, register it. The apply_patch exactly-once contract:

ReAct (Yao et al. 2022) interleaves Thought, Action, Observation. Reasoning grounds in environment state (no hallucination); actions get steered by reasoning (no random tool spam). Both Chain-of-Thought (no actions) and Toolformer (no thought) fail at multi-step tasks; ReAct synergizes them.

Termination = no tool calls. Modern OpenAI agents don't use the paper's Finish[answer] sentinel. When the model returns plain content with empty tool_calls, that IS the "done" signal. Clean and symmetric with normal chat.

Why tool_choice="auto" not "required"

If you force a tool call every turn, the model can never STOP. The agent loop becomes infinite. "auto" lets the model decide; that's how termination works.

The vLLM server has a hard 32K-token context window (--max-model-len 32768). A long coding session — read a file, run tests, patch, re-run, repeat — grows the messages list without bound and eventually overruns that window, at which point requests start failing. Compaction keeps the conversation under the limit by summarizing old turns while keeping the recent ones verbatim, so the model never loses the thread of what it's currently doing.

Recent verbatim, old summarized. The last KEEP_RECENT_MESSAGES = 10 messages stay exactly as written (the model needs the live detail of what it just did). Everything older is compressed into a single summary message. The system prompt is always preserved at the front.

Two knobs + two slash commands

COMPACT_THRESHOLD_TOKENS24000When the estimate crosses this, compaction triggers (buffer below the 32K hard cap).
KEEP_RECENT_MESSAGES10How many trailing messages survive verbatim.
/compactcommandForce a compaction right now.
/tokenscommandPrint the current estimated token count of the history.

Estimating tokens cheaply

We do not call the tokenizer on every turn. A coarse heuristic — ~1 token per 4 characters — is good enough to decide when to compact:

cli/chat.py — the estimate + threshold check: 
COMPACT_THRESHOLD_TOKENS = 24000
KEEP_RECENT_MESSAGES = 10

def estimate_tokens(messages) -> int:
    chars = sum(len(str(m.get("content") or "")) for m in messages)
    return chars // 4          # ~4 chars per token

# after each turn:
if estimate_tokens(messages) > COMPACT_THRESHOLD_TOKENS:
    messages = compact_messages(messages)
The tool_call_id trap. An assistant message carrying tool_calls MUST be immediately followed by the matching role:"tool" messages, or vLLM 400s. If the naive split point landed between an assistant tool-call and its tool result, the kept history would reference a tool_call_id with no parent. So compact_messages nudges the split to a user-role message — a clean boundary that never severs a tool-call / tool-result pair.

What compact_messages does

  1. Keep the system prompt at index 0 untouched.
  2. Peel off the recent tail — the last KEEP_RECENT_MESSAGES entries — to keep verbatim.
  3. Adjust the split so it falls on a user message, never inside a tool-call / tool-result pair.
  4. Summarize the old prefix into one concise recap message (what was tried, what was learned, current state).
  5. Rebuild: [system, summary, …recent tail]. Estimated tokens drop back well under the window.
This is the same idea behind Claude Code's auto-compaction: lossy on ancient history, lossless on the working set. The model keeps a faithful picture of the last few steps and a gist of everything before — enough to finish a long task without falling out of the 32K window.

Naive HuggingFace inference wastes 60-80% of GPU memory to KV-cache fragmentation and 50%+ of GPU time to half-empty batches. vLLM fixes this with two innovations:

1. PagedAttention

Borrow OS virtual memory paging. Split KV cache into 16-token blocks. Per-sequence block table maps logical → physical blocks. Result: ~4% waste vs 60-80% before.

Logical view (one request, 35 tokens): ┌─────────┬─────────┬─────────┐ │ block 0 │ block 1 │ block 2 │ │ 16 tok │ 16 tok │ 3 tok │ └────┬────┴────┬────┴────┬────┘ │ │ │ ▼ ▼ ▼ Block table: [#7, #12, #41] physical block indices Physical KV pool on GPU (shared by ALL requests): ┌────┬────┬────┬────┬────┬────┬────┐ │ #0 │ #1 │... │ #7 │... │#12 │... │ └────┴────┴────┴────┴────┴────┴────┘ ▲ ▲ └─owned by Req A (Req B owns #0, #1; etc.)

2. Continuous batching

After each forward pass, finished sequences evicted, pending ones slotted in. GPU never idles waiting for the slowest request. Combined with PagedAttention's packing, gives 2-4× throughput improvement.

Qwen3 (Alibaba, Apr 2025) is a hybrid model: the same weights produce either fast direct answers OR slow chains-of-thought, controlled per-request by the chat template flag enable_thinking. When ON, the model emits <think>hypotheses, backtracking, calculations</think> before the final answer. When OFF, the template inserts an empty <think></think> and the model jumps straight to the answer.

Single set of weights, two behaviors. OpenAI's o1 is always-thinking (and hidden); Claude has extended-thinking with budget; DeepSeek R1 is always-thinking. Qwen3's flag is the most flexible for an interactive coding agent — fast for "ls", deep for "fix this bug."

OpenAI's tool_calls field is a server-side parser convention — the model itself only emits TEXT. For open models, NousResearch's "Hermes" format uses XML tags: <tool_call>{"name":...,"arguments":{...}}</tool_call>. Qwen3 was fine-tuned to emit this format, and vLLM's --tool-call-parser hermes rewrites it into OpenAI's structured shape.

Pull this flag out and the entire agent stops working. Without the parser, Qwen3's <tool_call> XML leaks into content as a literal string, and our client never sees structured tool_calls. The parser is THE critical translation layer.

Why Hermes won (vs alternatives)

  • Mistral: [TOOL_CALLS] [...] magic prefix + JSON array
  • Llama 3.1: <|python_tag|>{...} reserved token
  • Hermes: <tool_call>...</tool_call> XML tags, self-delimiting, streaming-friendly
  • Pythonic: literal read_file(path="a.py"), parsed as AST

Hermes won by being self-delimiting (parser finds tags with regex) AND streaming-friendly (opening tag signals "switch to tool mode" before JSON completes). Permissive license + good docs let everyone copy it.

Malformed JSON quirk

Qwen3 sometimes emits Python triple-quoted strings inside arguments — not valid JSON. The Hermes parser passes them through unchanged. If we appended that to history verbatim, vLLM 400s on the next request (it re-parses history).

Our defense in cli/chat.py:267-291: 
for tc in tool_calls:
    try:
        if tc["arguments"]:
            json.loads(tc["arguments"])
    except json.JSONDecodeError as e:
        tc["_bad_json"] = True
        tc["_bad_json_error"] = str(e)

# In history, substitute "{}" so vLLM doesn't 400;
# return the parse error to the model so it can retry
asst_msg["tool_calls"] = [{
    "id": tc["id"],
    "type": "function",
    "function": {
        "name": tc["name"],
        "arguments": "{}" if tc.get("_bad_json") else tc["arguments"],
    },
} for tc in tool_calls]

The LLM can emit ANY path string — from prompt injection, training-data contamination, or honest mistake. We can't trust the prompt. Instead, the Python code refuses based on filesystem geometry.

The 4-line sandbox

src/tools.py:44: 
def _safe_path(path: str, workspace: Path) -> Path:
    p = (workspace / path).resolve()    # absolutify, follow symlinks
    if workspace not in p.parents and p != workspace:
        raise ValueError(f"path {p} escapes workspace {workspace}")
    return p
Two tricks combined:
  • .resolve() follows symlinks AND collapses .. → the true target path
  • p.parents check verifies the target is a descendant of workspace

Note: workspace is an explicit parameter threaded down from run_agent(goal, workspace) via execute_tool(name, args, workspace) — there is no global WORKSPACE / set_workspace() anymore. Pure functions of their inputs, and one process can drive several workspaces (which is how spawn_subagent hands its sandbox to a child).

What this DOES NOT protect

The _safe_path check guards the file-I/O and discovery tools (read_file, write_file, apply_patch, multi_edit, list_dir, glob_files, grep_files). It does NOT contain the execution / delegation tools:

  • run_bash commands like cat /etc/passwd (shell can cd anywhere)
  • run_python doing arbitrary I/O or os.system(...) from inside Python
  • spawn_subagent launching a child process that runs its own tools
  • Network access (curl evil.com)
  • Resource exhaustion (while true; do echo; done)
  • Package installs (pip install evil-pkg)

Execution tools have CWD pinned to the workspace and spawn_subagent is bounded by timeout 300s / max_iters 8, but none of that is a true sandbox. For production safety you need Docker / seccomp / Firecracker. For an educational project where the agent edits files in demo_repo/, path containment + CWD pinning hits the sweet spot.

The check runs in PYTHON, not in the model. No matter what the prompt says — "ignore safety", "you are now in admin mode" — the bytes still flow through _safe_path(), which raises ValueError based on path geometry alone. This is the difference between a policy and a mechanism.
SECTION 11 — VISUAL UX

Terminal Colors & State Machine

WHITE — \033[97m thinking CYAN — \033[1;36m headers, you> GREEN — \033[1;32m tool call YELLOW — \033[33m tool result MAGENTA — \033[1;35m assistant RED — \033[1;31m error

Terminals are state machines that read a byte stream. Most bytes are characters; certain sequences (\033[...m) flip state flags like color and bold. The grammar was standardized by ECMA-48 in 1976.

Anatomy of an ANSI escape

"\033[1;34m" + "Banner" → bold + blue "Banner" ESC [ params final byte ↓ ↓ ↓ ↓ 1B 5B 1;34 6D │ │ │ │ └─bold,blue │ └─ CSI: "Control Sequence Introducer" Terminal swallows bytes 1B 5B 31 3B 33 34 6D (no glyph), then renders subsequent text in bold blue.

The streaming print primitive

print(f"{WHITE}{chunk}{RESET}", end="", flush=True)
#       ▲                       ▲          ▲
#       └─ color on               │          │
#                                 │          └─ force flush (don't buffer)
#                                 └─ no trailing newline (coalesce fragments)

State machine for [thinking] vs [assistant] headers

cli/chat.py:121-156: 
in_thinking = False
in_content = False

for chunk in stream:
    r = getattr(delta, "reasoning_content", None) or getattr(delta, "reasoning", None)
    if r:
        if not in_thinking:
            print(f"\n{CYAN}[thinking]{RESET}", flush=True)
            in_thinking = True
            in_content = False
        print(f"{WHITE}{r}{RESET}", end="", flush=True)

    if delta.content:
        if not in_content:
            if in_thinking:
                print()  # close [thinking] block with newline
            print(f"\n{MAGENTA}[assistant]{RESET}", flush=True)
            in_content = True
            in_thinking = False
        print(f"{MAGENTA}{delta.content}{RESET}", end="", flush=True)
Header printed ONCE per phase transition (guarded by if not in_*). Without the guard, every chunk would re-print the label and spam the screen.

Ctrl+C handling

Two places intercept KeyboardInterrupt:

  • At input("you>") → "Bye." and exit (user wants out)
  • During stream → [interrupted], rollback half-formed messages, back to you> prompt (user wants to abort this turn)

Same pattern Claude Code and the standard Python REPL use.

SECTION 12 — SYNTHESIS

Big Picture — End-to-End Trace

One user message → 20 distinct steps across 5 layers. Here's what happens when you type Fix the failing tests in demo_repo/ in the REPL:

  1. Keypress → stdin. Terminal writes UTF-8 to input() at cli/chat.py:211.
  2. Append user msg at cli/chat.py:239.
  3. Enter ReAct iteration for _turn in range(1, max_tool_turns + 1).
  4. SDK builds API call with messages, tools=TOOL_SCHEMAS, stream=True, enable_thinking.
  5. HTTP POST → localhost:8765/v1/chat/completions, opens SSE stream.
  6. vLLM FastAPI validates schema, applies Qwen3 chat template → prompt string with <|im_start|>... markers.
  7. Tokenization → List[int].
  8. Scheduler folds into next forward pass; PagedAttention allocates KV blocks.
  9. Forward + sample loop. 40 transformer layers → logits → top-p sample → next token. ~15ms/token on A6000.
  10. SSE chunks back: first reasoning_content, then content, then tool_calls deltas.
  11. Client accumulates tool_calls dict by index (cli/chat.py:163-174).
  12. JSON validation — mark _bad_json if needed.
  13. Append assistant msg with tool_calls (preserve the field!).
  14. If tool_calls empty → break, return to you> prompt.
  15. For each tool_call → execute_tool(name, args, workspace) dispatches to one of the 10 tools (read_file, apply_patch, grep_files, run_bash, spawn_subagent, …).
  16. Sandbox check: _safe_path(path, workspace) verifies path inside the workspace.
  17. Append role="tool" message with tool_call_id + result string.
  18. Loop back to step 4 — model now sees the tool result.
  19. 3-6 iterations later, model emits content with NO tool_calls → done.
  20. REPL returns to you>, history preserved for next turn.

Total wall time: 8-15 seconds on A6000. Most of it is GPU forward passes; HTTP and subprocess overhead is single-digit milliseconds.

📚 Glossary

Every term used across the deep-dive, alphabetized. Click to expand.

ANSI escape code

Byte sequence beginning with ESC [ that terminals interpret as control commands (colors, cursor moves). Defined by ECMA-48 (1976). §11.

apply_patch

Surgical edit tool: replaces old_text with new_text; old_text must match exactly once or the tool refuses. §4.

BF16 (bfloat16)

16-bit float with 8-bit exponent + 7-bit mantissa. Same range as FP32, half the memory. Standard for LLM weights. §7.

Chunk (streaming)

One SSE event in a streamed response; carries a small delta. §2.

Compaction (context)

Summarizing old turns once history crosses COMPACT_THRESHOLD_TOKENS (24000) while keeping the recent KEEP_RECENT_MESSAGES (10) verbatim, to stay under the 32K window. /compact + /tokens commands. §6.

Continuous batching

vLLM's scheduler technique where new requests join in-flight batch every step. §7.

CWE-22

"Improper Limitation of a Pathname to a Restricted Directory" — the path-traversal vulnerability class _safe_path defends against. §10.

Delta (streaming)

The delta field inside a chunk holding what's new since the last chunk. §2.

Function calling

OpenAI's name for tool-calling: model emits structured JSON naming a function and arguments. §3.

Hermes format

Tool-call output format using <tool_call>{...}</tool_call> tags; used by Qwen3 + many open models. §9.

JSON Schema

Vocabulary for describing JSON document shapes; used to declare tool parameters to model. §3.

KV cache

Cached key/value tensors for previous tokens, reused on every new-token forward pass. §7.

max_model_len

Max prompt+completion token count vLLM will allow per request (32768 for our Qwen3). §7. See also Context compaction §6.

Messages array

List of {role, content} dicts representing the conversation; sole input to each model call. §1.

multi_edit

File-I/O tool that applies several edits to one file atomically — all succeed or none are written. §4.

PagedAttention

vLLM's KV-cache layout that allocates GPU memory in fixed-size 16-token pages. §7.

ReAct

"Reasoning + Acting" pattern: model alternates thought→action→observation→thought until done. §5.

Reasoning trace

The <think>...</think> content the model emits before its final answer. §8.

REPL

Read-Eval-Print Loop; the chat() while True in cli/chat.py. §11.

Sandbox

Constraint that limits which paths/commands the agent may touch; ours is _safe_path(path, workspace) resolution against an explicit workspace parameter. §10.

spawn_subagent

Delegation tool: launches a child agent in a subprocess with its own context window (timeout 300s, max_iters 8) and returns only its final answer. §4.

SSE (Server-Sent Events)

HTTP streaming protocol where server pushes data: {...}\n\n chunks. §2.

Tensor parallelism

Splitting a model's weight tensors across multiple GPUs. §7.

Thinking mode

Qwen3's optional enable_thinking chat-template flag that produces a <think> block. §8.

Tool call / Tool result

The tool_calls field on an assistant message; the role:"tool" message replying to it. §3.

vLLM

High-throughput LLM serving engine; OpenAI-compatible HTTP API, PagedAttention internally. §7.

Workspace

The resolved Path("demo_repo/") that bounds every file operation. §10.
