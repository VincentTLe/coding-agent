WHAT TO SAY (≈75s): Here's the core tension. A modern LLM is a fantastic writer — ask it for a function and it'll hand you clean, plausible code instantly. But being a good writer is not the same as being a good agent. Left to run on its own against a real codebase, it falls apart in predictable ways. It hallucinates tool calls — invents functions or arguments that don't exist. It loses track of state, forgetting what it already changed. Worst of all, it'll confidently declare broken work "done" — and when it hits an error, it tends to stall or spin instead of fixing it. So the research question is on the right: can a local, open-weight model — not a giant hosted API — actually become a reliable coding agent, and what engineering does that take? And why build it from scratch? Because the interesting part isn't gluing libraries together — it's understanding and controlling every piece myself: the reasoning loop, the tools, the sandbox, and the memory. If a framework hides it, I can't study it.

What It Does

Hand it a repo with failing tests. It runs the suite, reads the failures, edits the source, and re-runs — until green, then stops.

$ agent "fix the failing tests in this repo"

Verified end-to-end — fixed a buggy demo repo to 11/11 passing.

WHAT TO SAY (≈75s): So what does it actually do? I hand the agent a repository where the tests are broken, and give it one English instruction: "fix the failing tests." Watch the loop. First it reaches for a tool — run_bash — and runs pytest. Three of eleven pass; eight failing. Now it reasons: it reads the source to see what's going on. It finds the bug — an off-by-one and a missing None check — and applies a patch directly to the file. Then, crucially, it doesn't assume it's done — it runs pytest AGAIN to check its own work. Eleven of eleven, green. And it stops on its own, because the goal is met. Nobody told it how many steps to take — it decided, by observing the test output, that the job was finished. I ran exactly this and it took a buggy repo all the way to eleven out of eleven. That run-read-patch-verify cycle is the whole game.

The ReAct Loop — the heart

reason → act → observe → repeat

for _ in range(max_iters):           # safety net
    resp = model.chat(messages, tools=schemas)
    msg = resp.choices[0].message
    messages.append(msg)             # remember what it said
    if not msg.tool_calls:           # no tool? it's done
        return msg.content
    for call in msg.tool_calls:      # act + observe
        result = run_tool(call.name, call.args)
        messages.append({"role": "tool",
                         "tool_call_id": call.id,
                         "content": result})
  • The messages list IS the memory — the API is stateless, so we re-send the whole conversation every turn.
WHAT TO SAY (≈90s): This is the engine of the whole agent — four steps in a loop: reason, act, observe, repeat. We hand the model the conversation so far plus the JSON schemas for our tools. It reasons, and one of two things happens. If it returns plain content with no tool calls, it's finished — we hand that back. Otherwise it returns one or more tool_calls; we execute each, and append the output back into the conversation as a message with role "tool". Then we loop. The most important idea here: the model is stateless — the API remembers nothing between calls. So this messages list is the memory. Every turn we re-send the entire growing conversation; that's how it "remembers" what it read and did. Each result carries a tool_call_id — the pairing that tells the model which call this answer belongs to, since it may fire several at once. And the for-loop has a hard max-iters cap, so a confused agent can never spin forever.

The loop you just saw is completely generic — it only knows "call a tool by name." So adding an eleventh tool is a one-line registration; I never reopen the loop.

What Makes It an Agent, Not a Chatbot

Reliability engineering — the interesting part

  • Sandbox — _safe_path() confines every file op to one workspace (CWE-22 path-traversal defense).
  • Verifies its own work — runs pytest, reads the failures, patches, re-runs until green (tests as a feedback signal).
  • Survives long tasks — context compaction summarizes old history past ~24k tokens, keeps the recent 10 (fits the 32K window).
  • Recovers, doesn't crash — tools return "ERROR: ..." strings, never raise — so a bad call becomes feedback the model can fix.
WHAT TO SAY (≈90s): This slide is the heart of the project — the difference between a demo and something you can depend on. First, a sandbox: every file path runs through one function, _safe_path, that resolves it and rejects anything escaping the workspace — a real path-traversal defense, so the model can't write to your home directory by accident. Second, the one I care about most: it verifies its own work. It runs pytest, reads the failures, edits the code, and re-runs — the test suite becomes a feedback signal, the same loop a human uses. Third, long tasks blow past the context window, so past about 24k tokens it summarizes old history and keeps the recent ten messages — that's what lets it survive a long session in a 32K window. And fourth: tools never raise an exception that kills the loop. A bad command comes back as an "ERROR" string, which the model reads as more feedback and tries again. Together, these give you autonomy that keeps going — in the right direction.

Does It Actually Work?

You can't claim capability from 3 toy tasks

  • So we built a 627-task benchmark: 163 HumanEval+  +  424 MBPP (downloaded & converted)  +  37 hand-authored HARD tasks.
  • HARD = debugging, refactors, multi-file, DP, graphs, OOP, parsing.
  • Honest scoring: the test files are hidden from the agent while it works — it can't read them to hard-code answers — and restored only for grading.
  • Validation gate: every task is proven real — the reference solution passes, the empty stub fails.
WHAT TO SAY (≈90s): Three hand-picked demos prove nothing — so the real question is whether this holds up at scale. We built a 627-task benchmark: 163 from HumanEval+, 424 from MBPP — standard sets we downloaded and converted — plus 37 hard problems I wrote by hand: debugging, refactors, multi-file changes, dynamic programming, graphs, OOP, parsing. But the number only matters if the methodology is honest, so two things. First, the test files are hidden from the agent the entire time it's working — it physically cannot open the tests and hard-code the outputs — and they're only restored at grading time. That's the difference between measuring problem-solving and measuring cheating. Second, a validation gate runs before any task counts: the reference solution must pass and an empty stub must fail. If either is wrong, the task is broken and we throw it out — so every one of those 627 is a real, well-formed problem. That's what makes the next number trustworthy.

WHAT TO SAY (≈90s): Here's the payoff. On the full 627-task suite the agent passes about 80 percent — 501 of 627 — and remember, the tests are hidden while it works, so it can't cheat. But the single number isn't the interesting part; the shape is. Easy beats medium beats hard, a clean gradient. That graceful degradation is exactly what a real benchmark looks like — if it were luck or memorization, the curve would be flat or noisy. Now the research story. Early runs were worse, and I went into the eval traces to find out why. I expected buggy code. Instead, the dominant failure was the model just talking — replying in prose, explaining what it would do, never actually calling a tool. When I filtered to runs where it genuinely engaged a tool, it was about 92 percent correct. So the model was capable; it was just sometimes failing to act. I added one guardrail: if it answers without a tool call, nudge it to act — otherwise mark it no-action. That recovered most of the lost tasks. The headline: the gains came from diagnosing a tool-use failure in the traces, not from a better model.

Honest limitations & what I learned

  • No true tool parallelism — tools run one at a time per loop.
  • A single workspace — no isolation across concurrent tasks.
  • Toy-to-moderate task scale — not SOTA SWE-bench-level difficulty.
  • Open-weight model is stochastic — same prompt, different runs.

What I learned

  • Reliability is mostly engineering around an already-capable model.
  • Building from scratch made the failure modes concrete — I could see them, not guess.
WHAT TO SAY (≈60s): I want to be straight about the limits. There's no real tool parallelism — tools execute one at a time. There's a single shared workspace, so I'm not isolating concurrent tasks. The task scale is toy-to-moderate — not SWE-bench-scale repository surgery. And because it's an open-weight model with sampling, it's stochastic: the same task can pass one run and fail the next. Two takeaways. First, reliability turned out to be mostly engineering — the sandbox, the verify-loop, the error contract, the guardrail — built around a model that was already capable. Second, doing this from scratch is what made the failure modes concrete. I could read them in the traces, which is the whole reason I found the tool-use bug.
