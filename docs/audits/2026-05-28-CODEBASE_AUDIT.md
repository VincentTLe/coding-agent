# Codebase audit — coding-agent (multi-agent, adversarially verified)

_71 agents · 122 raised · **114 confirmed** · 8 refuted. Read-only audit run 2026-05-28._

## Overall health
Fundamentally sound, and notably so for a from-scratch academic ReAct agent. The owner's specific worry — over-complexity vs Pi-agent simplicity — is largely unfounded: the dependency graph is clean and well-layered (prompts.py and tools.py are leaf modules, src/agent.py is the single run_agent seam, eval/run.py and solve.py reuse it without duplicating the loop, and skillopt reuses seams cleanly). The CRITICAL sandbox invariant (_safe_path) is intact and correct. The real problems are NOT architectural bloat; they are (1) a small number of concrete data-integrity / observability bugs that bite the live unattended SkillOpt run specifically — 590/627 per-task logs are 0 bytes (verified on disk right now), 8 benchmark fixtures are currently left deleted/modified by an interrupted rollout (verified via git status), and partial/corrupt rollout files can silently poison the validation gate; (2) one genuine structural violation of the project's own "one product, no v1/v2" rule — cli/chat.py is a second hand-synced ReAct loop that has drifted (no finish/nudge/skill, bypasses models.json); and (3) one academic-integrity flag — the cited SkillOpt paper (arXiv 2605.23904) is almost certainly hallucinated, which the project's own CITATION.md already warns about. None of this corrupts the headline pass/fail scoring of a clean single run, but several items quietly degrade the SkillOpt experiment's diagnosability and reproducibility. The code is well-commented, readable, and the simplicity debt is minor copy-paste, not premature abstraction. This is a solid project with a handful of sharp edges concentrated in the eval/SkillOpt plumbing, not a structurally troubled one.

## Top issues (prioritized)

1. **[HIGH] 590/627 per-task eval logs are 0 bytes — agent traces silently lost (worker-reuse + logging.basicConfig bug)**  
   `eval/run.py:573-607, src/agent.py:196,316-339,397`  
   What: _setup_logging() calls logging.basicConfig only once per process (guarded by the _logging_ready global). ProcessPool 'spawn' workers are reused across tasks. The first task in a worker binds the StreamHandler to its redirected stderr; every later task re-enters redirect_stderr to a NEW file but basicConfig is skipped, so the handler still writes to the first task's now-closed stream. Verified on disk: 590/627 logs are 0 bytes. For an unattended SkillOpt run the per-task log is the ONLY way to tell no_action vs timeout vs wrong-solution vs crash apart; ~94% of traces are gone, and the optimizer's reflect() sees only the 300-char pytest tail.  
   Fix: In run_agent, attach a fresh logging.StreamHandler(sys.stderr) per call and remove it in a finally (re-binds to the current redirected stderr), OR call basicConfig(force=True) per run_agent, OR simplest: pass an explicit file handle down from evaluate_task and write to it instead of the root logger. Add a smoke assertion that produced logs are non-empty.

2. **[HIGH] Hard-kill between unlink and finally leaves benchmark fixtures deleted; --resume then scores against the corrupted tree (fixtures ARE corrupted right now)**  
   `eval/run.py:579-625, 920-967`  
   What: Hidden test files are unlink()ed (582-586) and restored only inside the with-block and in the finally (611-612, 625). A hard kill (SIGKILL/OOM/reboot) skips finally, leaving test_*.py deleted in eval/tasks. snapshot_files reads whatever is on disk per task, so a subsequent --resume run snapshots the test-less dir and scores it with no tests (pytest exit 5 -> guaranteed FALSE FAIL), and the deletion persists. This is live: git status shows 8 fixture files in eval/tasks/bench/ currently deleted/modified (he_085/088/096/099/110/118/130/135), so a crashed rollout has already corrupted those tasks. Self-propagating and silent; the --resume crash-recovery path is exactly what triggers it.  
   Fix: Make hiding crash-safe: MOVE hidden tests to test_x.py.hidden and restore by moving back; on startup scan for orphaned .hidden backups and restore them. Or run each task in a copied temp workspace so eval/tasks is never mutated. At minimum add a startup integrity check that warns when a task that should have tests has none, and git checkout the 8 corrupted fixtures before the next run.

3. **[MEDIUM] Partial/incomplete rollout result is cached and used as a real validation score (gate poisoning)**  
   `skillopt/loop.py:85-97`  
   What: _rollout runs eval/run.py with check=False and never inspects the return code or the result count. It only refuses to cache on TimeoutExpired or an empty file. If the subprocess dies after flushing SOME tasks (OOM/SIGKILL/host crash), results is non-empty, a score is computed over only the completed subset, and that wrong number is cached under (skill_hash, split) and used by the strict-> val gate and the slow-update gate. One flaky rollout can derail an epoch with no error surfaced. Compounded by _read_jsonl having no per-line try/except (a torn final line crashes the whole resumable run, unlike run.py's own load_done which guards it).  
   Fix: After reading results, verify len(results) == expected task count (count non-blank lines in tasks_file) before caching/scoring; if short, treat like the timeout case (return 0.0,[] uncached) or log a distinct 'incomplete_rollout'. Wrap json.loads per line in _read_jsonl in try/except json.JSONDecodeError, mirroring load_done.

4. **[MEDIUM] cli/chat.py is a parallel, drifted ReAct loop — violates the project's one-product/no-v1-v2 rule**  
   `cli/chat.py:604-819, 831-1204; src/agent.py:358-843`  
   What: The REPL reimplements the entire ReAct loop (turn cap, assistant-message build, tool_call/role:tool pairing, dispatch, termination) instead of reusing run_agent. The pairing invariant — which yields API 400s if broken — now lives in two hand-synced copies, and they have already diverged: chat.py has no finish-tool handling, no nudge/no_action guardrail, cannot inject a SkillOpt skill (uses SYSTEM_PROMPT, not build_system_prompt), and bypasses models.json/load_model_config (reads VLLM_* env directly, hardcodes max_tokens=2048/MAX_MODEL_LEN=32768). Net effect: the REPL behaves differently from the scored eval/solve path and can't demo an optimized skill — the headline feature. The scored paths (eval + solve.py) are unaffected, which keeps this medium not high.  
   Fix: Extract the shared one-turn scaffolding (assistant-msg build + pairing + finish/terminate) into a helper that both run_agent and chat() call, with a pluggable emit-one-turn callback (non-stream for agent, stream for REPL). At minimum have chat.py call build_system_prompt + get_client/get_model and recognize finish, so the REPL matches the agent's completion and config semantics.

5. **[MEDIUM] Optimizer _extract_json fence branch returns the first fenced dict without checking for 'edits'/'selected' — silent gradient loss**  
   `skillopt/optimizer_llm.py:64-71`  
   What: The code-fence branch runs first and returns ANY dict in the first ```...``` block, unconditionally. The 'prioritize a dict with edits/selected' logic exists only in the later raw_decode loop, which is never reached when a fence matches. Qwen3 in reason-out-loud mode commonly fences a thinking/example JSON before the real answer; in that case the wrong dict is returned, .get('edits',[]) is [], the step proposes zero edits, candidate==current, the gate rejects, and no error is raised. On an unattended run this can quietly turn many steps into no-ops. The whole module also swallows every exception with zero logging, so a dead optimizer endpoint or a config typo (AGENT_OPTIMIZER_MODEL) makes the run a silent no-op indistinguishable from 'converged'.  
   Fix: Apply the edits/selected priority inside the fence branch (only return a fenced dict if it has 'edits' or 'selected'; otherwise fall through). Better: scan ALL fenced blocks + bare candidates together and return the first dict with 'edits'/'selected', falling back to 'any dict' only at the end. Add lightweight stderr breadcrumbs at each swallow point so systematic failures are visible.

6. **[MEDIUM] Per-task log filenames collide across SkillOpt rollouts; report prose hard-codes statistical conclusions that can contradict the numbers**

Make the report's mechanism/noise-floor sentences conditional on p_so<0.05 and sign(delta) and per-pair flips<=noise_flips, mirroring the auto-verdict block. Derive the val N instead of the hardcoded '12 task'.

8. **[HIGH] repeats>1 with jobs>1 races multiple workers on the same in-place task_dir**  
   `eval/run.py:959-1006`  
   What: The work list is the full tasks x repeats product, all submitted at once. With --repeats K --jobs N>1, futures for (tid,0..K-1) of the SAME task run concurrently against the same on-disk dir (snapshot/unlink-tests/agent-writes/restore/remove_extras), with no per-task lock or per-repeat copy. ## Architecture & system design
The core is genuinely clean and Pi-style: leaf modules (prompts.py, tools.py), a single `run_agent` seam reused by eval/run.py and cli/solve.py, and a skillopt package that reuses seams correctly (subprocess to eval/run.py for rollouts, imports get_client/get_model and discover_tasks/rel_id, consumes eval's JSONL as a data contract). The one-product/no-v1-v2 rule holds for the production path. **The single real violation is cli/chat.py** — a second, hand-synced ReAct loop that has drifted from src/agent.py (no finish/nudge, bypasses models.json, can't inject a skill). The fix is to share the one-turn scaffolding, not to delete the REPL (it has legitimate streaming/Ctrl-C/compaction needs run_agent doesn't serve). Minor architecture debt: examples/06_chat.py is dead-on-import (imports removed `set_workspace`, 2-arg execute_tool), and there's doc-level drift (10-vs-11 tools, dangling examples/05_agent_loop.py references).

## Bugs
- **Final-turn finish() misclassified as max_iters** (agent.py:743): on `i == max_iters`, the blanket `break` fires before finish detection, so a genuinely-finished run is logged as max_iters. Pure diagnostic mislabel (zero pass/fail impact), but it biases the failure-mode breakdown SkillOpt relies on. The edit-tool justification doesn't apply to finish (it touches nothing).
- **resp.choices[0] outside the OpenAIError handler** (agent.py:597-615): an HTTP-200 empty-choices response (a real vLLM-under-load mode the author already guards in the *streaming* path) raises IndexError that escapes the api_error path — agent_crash in eval, hard crash in solve.py/__main__.
- **No context-window trimming in run_agent** (agent.py): context_window is dead config; history grows unbounded and a large read_file can overflow the 32768 window, mislabeled api_error. chat.py has compaction; the path eval/SkillOpt use does not.
- **Gate-poisoning from partial rollouts** and **_extract_json fence bug** (covered in top_issues) are the two SkillOpt logic bugs that can silently corrupt accept/reject decisions.

## Simplicity & dead code
The owner's over-complexity worry is mostly unfounded. run_agent is ~485 lines but ~70% is deliberate teaching comments (an explicit project value); the executable body is ~72 LOC of mostly-linear guard-and-return logic. No premature abstraction. The real debt is small copy-paste: run_bash/run_python share byte-identical output formatting; grep_files/glob_files duplicate the 50-line truncate idiom; a preview-truncate one-liner recurs 4x with scattered magic numbers; chat.py duplicates client/config setup. Genuine dead code is tiny: `return f""` + unused exception bind in optimizer_llm._call; `slow_samples` is a wired-but-never-used CLI flag/param; `max_between` unused in report.py; redundant `% n` in splits apportionment.

## Robustness
The blanket "never kill the loop" exception-swallowing in the optimizer is sound policy but pairs with **zero logging**, so a dead endpoint / parse miss / all-sanitized-edits are indistinguishable and a misconfigured run looks like 'converged'. _read_jsonl lacks the per-line guard that run.py's own load_done has. No hard per-task wall-clock kill in run.py (bounded by SDK defaults, so not an infinite hang, but the --agent-timeout contract isn't truly enforced; model-chosen run_bash timeouts can overshoot). Several low-sev unguarded reads (skill_path, models.json, --tasks-file) crash instead of degrading. These are real but mostly low/medium and concentrated off the hot scoring path.

## Blind spots (observability, data integrity, reproducibility)
This is where the sharpest real issues live and they hit the *live* run: 590/627 zero-byte logs (verified), 8 currently-corrupted benchmark fixtures (verified via git status), log-filename collisions across rollouts, partial-rollout gate poisoning, scratch reused across optimize() runs so --resume can consume stale results, and report prose that can contradict its own numbers. Plus reproducibility gaps: no .python-version pin (with a stale 'Python 3.9' comment vs requires-python>=3.12), undocumented AGENT_MODEL/AGENT_OPTIMIZER_MODEL knobs, ModelConfig.temperature/context_window loaded but never used, and eval --temperature defaulting to None (non-greedy) — though skillopt correctly forces --temperature 0, so the experiment itself is fine. And the academic-integrity flag: the hallucinated SkillOpt citation.

### [HIGH] 590/627 per-task eval logs are 0 bytes — agent traces silently lost (worker-reuse logging bug)
- **file:** `/home/tle/code/coding-agent/eval/run.py:573-607` · _Cross-cutting blind spots_
- **what:** evaluate_task() opens its per-task log with redirect_stdout/redirect_stderr, and the agent's trace is emitted via the `logging` module (src/agent.py log.info), configured by _setup_logging() in run_agent. But _setup_logging() runs logging.basicConfig only ONCE per process (guarded by the module global `_logging_ready` in src/agent.py:196,316-339). ProcessPool 'spawn' workers are REUSED across many tasks. The first task in a worker runs basicConfig while its stderr is redirected into that task's log file, so the StreamHandler binds to that first file object. Every subsequent task in the same worker re-enters redirect_stderr to a NEW file, but basicConfig is skipped (guard already True), so the handler still writes to the first task's now-closed stream. Result: only the first task per worker captures a trace; all later tasks get 0-byte logs. Confirmed on disk: 590/627 logs are 0 bytes; the live run after 18:00 today shows 72 zero vs 8 non-zero (≈ jobs count get a trace, rest empty).
- **why:** For an unattended multi-hour SkillOpt run, the per-task log is the ONLY way to debug why a task failed (no_action vs timeout vs wrong-solution vs crash). Losing 90%+ of traces means a failed run is essentially un-diagnosable after the fact, and the optimizer's reflect() only sees the 300-char pytest tail, not the agent's reasoning. It also makes the '0-byte logs' symptom look like a disk/permissions problem when it is a logging-binding bug.
- **fix:** Don't rely on logging.basicConfig+redirect. Either (a) in run_agent attach a fresh logging.StreamHandler(sys.stderr) each call and remove it in a finally (so it re-binds to the current redirected stderr per task), or (b) drop _logging_ready guard and call basicConfig(force=True) per run_agent, or (c) simplest: have cprint/log write to an explicit file handle passed down from evaluate_task instead of going through the root logger. Verify by asserting every produced log file is non-empty for a small run.
- **verifier:** I tried to refute this and could not; the code and disk both confirm it.

### [HIGH] repeats>1 with jobs>1 races multiple workers on the same task_dir (in-place snapshot/hide/restore)
- **file:** `eval/run.py:959-1006` · _Eval harness correctness & concurrency (eval/run.py)_
- **what:** The work list is the full cartesian product tasks x range(repeats) (lines 961-972) and ALL items are submitted to the pool at once (line 1006). When --repeats K and --jobs N>1 are combined, the futures for (tid,0),(tid,1),...,(tid,K-1) of the SAME task run concurrently. Each worker (evaluate_task) snapshots, unlinks the hidden test files (line 582-586), runs the agent which writes into task_dir, restores hidden tests (611-612), then restore_files+remove_extras (617,625) on the SAME on-disk directory. - **fix:** Either give each repeat an isolated working copy (copy task_dir to a temp dir, run there, grade there) so concurrent repeats never share disk; or, if in-place must stay, refuse the combination: if args.repeats>1 and args.jobs>1, fall back to serializing repeats of the same task (group work so no two items share a task_dir run concurrently) or print a hard error/warning at startup.

### [HIGH] Hard kill (SIGKILL/OOM) between unlink and finally leaves hidden tests deleted; next --resume snapshots the broken tree
- **file:** `eval/run.py:579-586, 622-625, 920-967` · _Eval harness correctness & concurrency (eval/run.py)_

Fixtures are git-committed so recovery is possible, but nothing in the harness detects or repairs it.

- **verifier:** Confirmed against the actual code in /home/tle/code/coding-agent/eval/run.py. The full causal chain holds:
