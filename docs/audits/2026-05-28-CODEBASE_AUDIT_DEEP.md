Yes. The deeper pass found two genuinely serious things the broad pass missed, both in the substrate the owner cares most about. (1) The MBPP half of the benchmark leaks 2 of ~3 graded asserts into the agent-visible Goal while declaring "## Tests: hidden" — the anti-cheat claim is materially false for ~93% of MBPP and the two benchmark halves are not measuring the same thing. ## Pillar assessment
## Where the three pillars actually stand after both audits

**AUDITABILITY — weakest pillar; structurally not yet trustworthy.**
A results artifact cannot answer "what produced these numbers?" The per-task result dict records task/passed/finish_reason/duration/pytest_tail but **no model, temperature, max_iters, agent_timeout, or git SHA** (run.py:629-644; --temperature even defaults to None so effective sampling is unrecorded). Every A/B claim in report.py compares two JSONL files whose producing configs are invisible. On the learning side, the **optimizer's prompt and raw response are never persisted** (optimizer_llm.py:47 returns only content, callers discard it), and **accepted-edit content is never logged** — only `n_edits` + `target[:60]` (loop.py:205-207; skill.py:131), with `current_skill.md` overwritten every step. So the single learnable artifact of SkillOpt — the human-readable skill — cannot be attributed to the edits that produced it, and a no-op step cannot be distinguished between "model returned junk," "JSON extraction dropped good edits," and "sanitizer rejected all." validate_tasks quarantines tasks (shutil.move) with **no manifest** of what was removed or why. pytest_tail keeps only `output[-1000:]`, which can cut the failing assert for the giant EvalPlus single-function tests. *What's missing to be trustworthy:* a run-header/sidecar with full config + git SHA per results file; per-step persistence of optimizer IO and accepted-edit content + per-step skill snapshots; a validate report/quarantine manifest.

**VERIFICATION — the agent's self-check and the harness scoring disagree by construction.**
The agent self-verifies with run_bash at a 600s budget; the harness scores with a hard-coded 60s pytest cap (run.py:495) treated identically to a logic failure — so correct-but-slow EvalPlus solutions are scored FAIL and a slow-but-correct *reference* is quarantined as BROKEN. The OpenAI client has **no per-request timeout/max_retries** (agent.py:292), and time_budget_s is only checked *between* turns (agent.py), so neither the agent nor the harness (`fut.result()` with no timeout) can interrupt a stuck call — the documented "per-task wall-clock cap" does not exist as a hard cap. The core SkillOpt acceptance gate's only test is **tautological** — it re-implements gate() inline and never imports loop.optimize (test_skillopt.py:128-140) — so flipping `>` to `>=` would not fail any test. read_hide_tests, the load-bearing anti-cheat switch, has **zero tests** and the in-code docstrings document a `## Tests: hidden` inline format the exact-match parser silently rejects. *What's missing:* align scoring/self-verify timeouts and emit a distinct timeout reason; a real per-request + hard per-task wall cap; tests that exercise the actual gate, hide-tests, and summary math.

**EVALUATION — the headline numbers are partly built on leaky/inconsistent ground.**
The MBPP goal leak (convert_benchmark.py:257-259) inflates the larger benchmark half and breaks HE-vs-MBPP comparability. run_pytest scores an all-skipped/zero-collected session as PASS (exit 0), exploitable on the visible curated + legacy tasks whose test files survive. report.py never checks that the three arms cover the same task set, mixes an unpaired Δ with a paired McNemar over the intersection against a mismatched denominator, and the mandatory noise-floor verdict rests on a hand-run rerun whose config is unverifiable. --resume keys only on (task,repeat_idx), so a single out-file silently becomes a chimera of two skills/configs. The SkillOpt **overloaded 0.0 sentinel** means a transient infra blip on the seed rollout fabricates a phantom 0% baseline (auto-accepting the first non-zero candidate and inflating reported lift) or false-rejects good candidates — with no `rollout_failed` event to tell which. *What's missing:* stop leaking graded asserts (or stop calling those tasks hidden); parse pytest summary counts not just exit code; enforce equal task sets across arms; distinguish infra-failure from a real 0.0; persist config so resume/A-B comparisons are provably homogeneous.

**Net:** the agent and harness are individually reasonable, but the surrounding evaluation/learning substrate is not yet self-describing or internally consistent enough to *defend* a number to a skeptic. The highest-value fixes are cheap (record run config + optimizer IO; one shared truncation/timeout/manifest-parse helper; a non-tautological gate test; stop the MBPP leak) and would move all three pillars at once.

### [HIGH/correctness] snapshot/restore treats all files as UTF-8 text and corrupts binary files on restore
- `/home/tle/code/coding-agent/eval/run.py:352-360, 401-419`
- what: snapshot_files reads every file with read_text(encoding='utf-8', errors='replace'); restore_files writes them back with write_text(content, encoding='utf-8'). Any non-UTF-8 file is irreversibly corrupted on restore. Confirmed by roundtripping the real committed eval/tasks/bench/mbpp_229/__pycache__/re_arrange_array.cpython-312.pyc: 567 bytes in, 715 bytes out, not equal. The finally-block restore runs on EVERY task even on a clean single run, so a binary test fixture (.png/.pkl/.npy/.db/.parquet) shipped with a task is permanently mutated and the next scoring run reads garbage.
- why: Any task with a binary fixture yields arbitrary wrong scores on subsequent runs and makes the eval non-idempotent (mutates the committed tree). Today it actively corrupts the committed .pyc files, compounding finding #1.
- fix: Snapshot/restore in binary mode (read_bytes/write_bytes) and key snap on bytes, OR skip non-text/binary files entirely (and never snapshot __pycache__). At minimum, exclude files that fail strict UTF-8 decode and restore them via byte copy.

### [HIGH/auditability] Optimizer LLM prompt and raw response are never persisted — textual gradient is unauditable
- `skillopt/optimizer_llm.py:37-49, 139-159, 162-174, 177-193`
- what: _call() returns only resp.choices[0].message.content (line 47) and reflect/merge/clip/_slow_update all immediately pipe that string through _extract_json/_sanitize_edits and throw the raw text away. The loop never receives or logs the optimizer's prompt or response. So when a step is a no-op (0 edits applied), there is no way after the fact to tell whether the optimizer LLM returned junk, returned valid edits that the fence/raw_decode path missed, or whether _sanitize_edits rejected them all. The 'textual gradient' — the core mechanism of SkillOpt — leaves no trace.
- why: A surprising SkillOpt result (e.g. score never moves, or moves the wrong way) cannot be diagnosed. You cannot distinguish 'the optimizer model is bad at this' from 'our JSON extraction is dropping good edits' from 'sanitization is too strict' — which are completely different fixes. This is the single biggest debuggability hole in the training loop.
- fix: Have _call (or reflect/merge/clip) return/emit the (system, user, raw_response) triple, and have loop.py log() it per step (truncated if needed) into trajectory.jsonl or a sibling optimizer_calls.jsonl. At minimum log the raw response length and a hash so empty/garbage responses are visible.

### [HIGH/auditability] Accepted edits' content is never logged; only n_edits + target[:60] reports — learned rule is unrecoverable from trajectory
- `skillopt/loop.py:192-208`
- what: On an accepted step, the step log records decision, cand_score, n_edits=len(clipped) and edit_reports, but NOT the actual `clipped` edit objects (op/target/content). edit_reports come from apply_edits and only contain {op, target[:60], status} (skill.py:131) — the content that was actually appended/inserted (the new RULE) is never captured. The full skill text is written only to current_skill.md (line 208), which is OVERWRITTEN every step, so after a multi-step run you have one final blob and no per-step deltas. You literally cannot answer 'what rule did the optimizer learn at step 3 that improved val?'
- why: The entire point of SkillOpt is to learn a human-readable skill document. If you cannot attribute each accepted improvement to the specific text edit that caused it, the trajectory is unauditable and the headline 'skill helped/didn't help' result cannot be explained or defended. Diffing skill files is also impossible because only the final current_skill.md survives.
- fix: Add `"edits": clipped` to the step log record. Additionally write a per-step skill snapshot (e.g. run_dir/steps/e{epoch}_s{step}.md) instead of/in addition to overwriting current_skill.md, so the skill version chain is reconstructable.

### [HIGH/evaluation] --resume skips (task,repeat) regardless of skill/config, silently mixing versions in one scored out-file
- `eval/run.py:703-745, 955-972, 992`
- what: load_done() builds the 'done' set keyed ONLY on (r["task"], r.get("repeat_idx",0)). It ignores skill_path, max_iters, temperature, and agent_timeout, all of which are recorded per-row (skill_path is even written at line 643 'phục vụ so A/B'). The second invocation skips every task the first finished and appends the rest under the NEW skill — the file now contains seed-skill rows AND optimized-skill rows scored as one arm. Either (a) include a config fingerprint (skill_path, max_iters, temperature, agent_timeout, plus a code/git hash) in the done-key and refuse to skip rows whose fingerprint differs, or (b) at startup compare the current run's config against the config recorded in existing rows and abort with a clear error if they differ. At minimum, write a run-level header/sidecar recording the config and validate it on resume.

### [HIGH/evaluation] MBPP goal leaks 2 of ~3 graded test asserts into agent-visible spec while task is declared 'Tests: hidden'
- `eval/convert_benchmark.py:257-259 (also write_task 124-132; consumed via run.py read_goal 243-254 → run_agent)`
- what: emit_mbpp builds goal = f"{text}...Example checks:\n{examples}" where examples = "\n".join(test_list[:2]) — the first 2 raw assert statements from the graded test_list. This entire string is written into task.md under '## Goal', and read_goal() returns the full Goal section verbatim to run_agent(). Meanwhile write_task() writes '## Tests\nhidden' for every MBPP task, and evaluate_task() physically deletes the test_*.py files so the agent supposedly cannot see the tests. I confirmed against the cached dataset: ALL 427/427 MBPP tasks embed 2 real asserts; the graded test runs the WHOLE test_list (397 tasks have exactly 3 asserts, the rest 4-7). So for the typical task, 2 of the 3 graded assertions (exact inputs AND expected outputs) are handed to the agent even though tests are 'hidden'.
- why: The hidden-tests mechanism is the eval's central anti-cheat / implement-from-spec integrity claim. For the entire MBPP half of the suite that claim is materially weakened: an agent can read 2 concrete I/O pairs and is far more likely to pass (and could memorize/hard-code at least those cases), so the reported MBPP pass-rate is inflated relative to the true 'implement from spec' difficulty. HumanEval, by contrast, only exposes the natural docstring — so the two halves of the 627-task benchmark are not measuring the same thing, making aggregate pass-rate comparisons inconsistent.
- fix: Either (a) drop the 'Example checks:' block entirely so MBPP matches HumanEval's spec-only goal, or (b) if examples are desired for fairness, scrub the expected RHS (show only the call form, not '== expected') and/or include only example(s) that are NOT in the graded test_list. At minimum, stop declaring these tasks 'hidden' if you are going to leak graded asserts — the metadata should reflect reality.

### [HIGH/verification] validate_tasks treats a transient 60s pytest timeout as 'BROKEN' and (with --quarantine) permanently deletes the task from the suite
- `eval/validate_tasks.py:143,154,158,165,238-254 (run_pytest timeout path eval/run.py:474-476)`
- what: validate_one calls run_pytest(task_dir) for the reference phase. run_pytest returns (False, 'ERROR: pytest timed out after 60s') on a 60s timeout — indistinguishable from a genuinely failing reference. validate_one then computes ok = ref_pass and not stub_pass → ok=False, note='BROKEN: reference solution does not pass — ...'. In main(), if --quarantine is set, every 'bad' task is shutil.move()'d into _quarantine/ (lines 244-254), which discover_tasks() then permanently skips. There is no retry and no separation of 'timeout' from 'reference is actually wrong'. validate is run with --jobs 16 (the documented invocation), so under CPU contention a correct task can exceed 60s, get flagged BROKEN, and be silently evicted from the 627-task substrate.
- why: Auditability/verification: the suite size and composition become nondeterministic and machine-load-dependent. A loaded validation run silently shrinks the benchmark, and the only signal is a one-line [INVALID] print that looks identical to a real broken task. Re-running on a faster machine yields a different task set, undermining reproducibility of every downstream pass-rate.
- fix: Have run_pytest signal timeout distinctly (e.g. return a sentinel or raise), and in validate_one treat timeout as note='TIMEOUT (not quarantined)' with ok=False but EXCLUDED from the --quarantine move list (or retried N times with a longer budget). Never auto-move a task whose only failure was a timeout.

### [HIGH/verification] OpenAI client built with no request timeout/max_retries — one stalled vLLM call can hang a turn ~30 min, defeating time_budget_s
- `src/agent.py:288`
- what: _client = OpenAI(base_url=cfg.base_url, api_key=cfg.api_key) is constructed with no `timeout=` and no `max_retries=`. The OpenAI Python SDK defaults to a 600s per-request timeout and 2 automatic retries (3 attempts total). So a single client.chat.completions.create() (agent.py:597) against a wedged or overloaded vLLM server can block ~600s x 3 ≈ 30 minutes — entirely INSIDE one turn. The between-turns time_budget_s check (agent.py:495) cannot fire while blocked inside the API call, and the harness has no out-of-band timeout (see related finding). models.json even exposes a context_window/temperature but no request-timeout knob.
- why: vLLM on a shared GPU (the repo's deployment) routinely stalls under queueing/OOM. A handful of stalled connections during a 627-task or SkillOpt run can each silently consume up to half an hour, blowing both --agent-timeout and SkillOpt's sub_timeout, and producing a 'duration_s' of ~1800s that contradicts the configured cap. This is the single most likely real-world hang in an unattended run.
- fix: Construct the client with an explicit per-request timeout derived from time_budget_s (e.g. OpenAI(..., timeout=min(120, time_budget_s), max_retries=1)) or pass timeout= per create() call. Surface it in models.json so it is config-tunable like the other knobs.

### [HIGH/consistency] Inconsistent output capping: read_file/run_bash/run_python return UNBOUNDED text straight into the model context
- `src/tools.py:159-162, 257-275, 788-798 (and consumed at src/agent.py:799-814)`

### [HIGH/auditability] Infra-failed rollout (timeout/incomplete/empty-split) is indistinguishable from a genuine 0.0 score — silently false-rejects candidates and poisons the audit trail
- `skillopt/loop.py:96-105, 194-203, 222-223`
- what: _rollout returns the same sentinel (0.0, []) for (a) a subprocess TimeoutExpired (line 97), (b) an incomplete run where n_done<n_tasks (line 105), and (c) an empty/zero-result run (line 105). - why: VERIFICATION/AUDITABILITY: the whole point of the val gate is a trustworthy accept/reject signal. - fix: Make _rollout distinguish failure from a real score (e.g. return None or raise a RolloutError on timeout/incomplete/empty), and in optimize() skip the step / log an explicit {"event":"rollout_failed","phase":"gate"} record instead of folding it into a normal reject.

### [MEDIUM/consistency] Optimizer prompt mis-defines finish_reason "timeout" as "ran out of steps" (it is wall-clock; "steps" is max_iters) — teaches a wrong corrective rule for every timeout failure

### [MEDIUM/consistency] Five harness-emitted finish_reason values (max_iters, api_error, agent_crash, worker_error, unknown) are fed to the optimizer but never glossed in its prompt
- `/home/tle/code/coding-agent/skillopt/optimizer_llm.py:144-152`
- what: The optimizer's case line emits the raw finish_reason for every case: optimizer_llm.py:151 `passed={...} finish_reason={c.get('finish_reason')}`, sourced from loop.py:60 (_cases copies r.get('finish_reason') straight through from the eval result dict).
