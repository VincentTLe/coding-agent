Coding Agent from Scratch

A local, open-weight model that I turned into a working coding agent

I wrote the loop, the tools, the sandbox, and the benchmark myself, with no framework

Vincent Le · Knox College · Math/Stat 361 · Advisor: Prof. Andrew Leahy

WHAT TO SAY (≈25s): Hi everyone, I'm Vincent. For my Math/Stat 361 research with Professor Leahy, I built a coding agent from scratch. It takes a local, open-weight model running on my own GPU and makes it do real software work. The ReAct loop isn't my invention; Claude and Codex use the same pattern. What I did was write every part myself so I can explain it, and then measure how well it works without fooling myself. The measuring part is what I care about most today.

WHAT TO SAY (≈70s): A modern LLM is a strong writer. Ask for a function and you get clean code right away. But working against a real codebase is a different job, and the model fails in predictable ways: it invents tool calls that don't exist, forgets what it already changed, and reports broken work as done. So my research question is whether a local, open-weight model can be made into a reliable agent, and what that actually takes. Why from scratch, when Claude and Codex exist? Three reasons, shown on the bottom row. LOCAL means it runs on my own GPU and the code never leaves the machine. TRANSPARENT means you can watch every tool call and every reasoning step, which matters for a research project. FROM SCRATCH means there's no LangChain hiding the parts, so I can read and explain every line. It isn't as capable as Claude, which was never the goal.

What it does

Give it a plain-English spec, with no tests. It writes the code, then writes and runs its own check, and stops when the check passes.

$ agent "write int_to_roman and roman_to_int, and prove they round-trip" → write_file roman.py # both functions + a round-trip check → run_bash python roman.py 4, 9, 58, 1994, 3999: all PASS finish round-trip holds, stopped on its own
WHAT TO SAY (≈60s): I give it one plain-English spec and no tests: write int_to_roman and roman_to_int for 1 to 3999, and check that they round-trip. Watch what it does. It writes both functions in one file, and at the bottom it adds its own check: take a number, convert it to a Roman numeral, convert that back, and confirm you get the original number. Then it runs the file, and all five values pass. It calls finish on its own because its check passed. What matters here is that it never saw a test from me. It wrote the code and its own way to check it, then ran it, the same way I would.

WHAT TO SAY (≈50s): The whole system fits in five boxes. I type to it from a terminal. That goes to the Agent, which is the ReAct loop I wrote. The Agent queries a vLLM server running Qwen3-14B locally, with a 32K context, over an OpenAI-compatible API. On that two-way arrow, the server is stateless and remembers nothing between calls, so all the memory lives in the loop, not the model. The Agent also calls the tools, and their results come back in as the next thing the model sees. Those tools run inside a sandboxed workspace. So the loop holds the memory and makes the decisions, the model is just something it queries, and the tools do the actual work.

The ReAct loop

REASON
think
ACT
call tool
OBSERVE
read result
REPEAT
loop
for _ in range(max_iters):        # safety net
    msg = model.chat(messages, tools)
    messages.append(msg)          # remember!
    if not msg.tool_calls:        # no tool = done
        return msg.content
    for call in msg.tool_calls:   # act + observe
        r = run_tool(call.name, call.args)
        messages.append({"role": "tool",
            "tool_call_id": call.id, "content": r})
  • The messages list holds the memory. The API is stateless, so we re-send the whole conversation each turn.
WHAT TO SAY (≈65s): The loop has four steps that repeat: reason, act, observe, then go again. I send the model the conversation so far plus the JSON schemas for my tools. It either returns plain text, which means it's done, or it returns tool calls. I run each call and append the result as a message with role tool, then loop. The model is stateless: the server keeps nothing between calls, so this growing messages list is the memory, and every turn I re-send the whole conversation. That's how it remembers what it read and did. The for-loop also has a hard max-iters cap so a stuck agent can't run forever. I wrote this part myself because a framework would hide it, and then I couldn't study how it works.

WHAT TO SAY (≈65s): Eleven tools in four families. I won't read them all; the grouping is what matters. File I/O to read and edit code. Discovery to find your way around a repo. Execution, which is bash and Python, to actually run things. And delegation plus finish. Replying in prose does not end a session; only calling finish does. Each tool is a function with a JSON schema in an append-only registry, so I can add a tool without changing the loop. The sandbox is the safety part. Every file path goes through one function, _safe_path, which resolves it and rejects anything that points outside the workspace. So if the model tries to read dot-dot-slash etc-passwd, the read is rejected. And a failing tool returns an ERROR string instead of throwing, so the model reads it as feedback and tries again.

What makes it reliable

After each edit it reruns pytest and keeps fixing until the tests pass, so it checks its own work.
On a long task it stays inside the 32K window by summarizing old history past about 24K tokens and keeping the last 10 messages.
A failing tool returns an "ERROR: …" string instead of throwing, so one bad call becomes feedback and the loop keeps going.
WHAT TO SAY (≈65s): These three things are what make it dependable rather than a one-off demo. The first is the one I care about most: it checks its own work. After it edits the code, it reruns pytest and keeps fixing until the tests pass, the same way I would. The second is context. A long task runs past the 32K window, so past about 24 thousand tokens it summarizes the old history and keeps the last ten messages, which lets it finish. The third is error handling. A failing tool returns an ERROR string instead of throwing, so a bad call becomes feedback the model can act on instead of a crash. That is most of where the reliability comes from, together with the sandbox.

Does it actually work?

I built a 627-task benchmark to measure it

  • The 627 tasks are 163 from HumanEval+, 424 from MBPP, and 37 hard ones I wrote by hand (debugging, refactors, multi-file, DP, graphs, OOP).
  • While the agent works, the test files are hidden, so it can't open them and copy the answers. They come back only for grading.
  • Before a task counts, I check it is real: the reference solution must pass and an empty stub must fail.
WHAT TO SAY (≈60s): A few hand-picked demos don't show much, so I built a benchmark of 627 tasks: 163 from HumanEval+, 424 from MBPP, and 37 hard ones I wrote by hand. Two things keep the number honest. First, the test files are hidden from the agent the whole time it works, so it can't open them and copy the expected outputs; they only come back at grading time. Without that, I would be measuring copying instead of problem-solving. Second, before a task counts I check that the reference solution passes and an empty stub fails, so every one of the 627 is a real, working problem. That sets up the number on the next slide.

WHAT TO SAY (≈70s): On the full 627-task suite the agent passes 67.3 percent, 422 of 627, with the tests hidden the whole time. The 95 percent confidence interval is 64 to 71. By slice, HumanEval is about 80, MBPP about 67, and my hard hand-written set is 21.6. That low number is expected; those problems are genuinely hard. The part I find more interesting is at the bottom. When I read the failure traces, the most common failure wasn't bad code. It was the model writing an answer in prose without calling a tool, 66 times out of 627. I added a guardrail that pushes it to act, and that fixed most of them. So the improvement came from spotting a tool-use bug, not from a bigger model. I'm especially careful about what's on the next slide.

WHAT TO SAY (≈75s): An earlier version of this slide said 79.9 percent, and it was wrong. While hardening the project I found a bug in my own benchmark: for about 93 percent of the 424 MBPP tasks, two of the three graded assert statements were showing up in the goal text the agent could read. So it could match the expected outputs instead of solving the problem. I didn't find it by luck; it came out of a multi-agent audit and a cross-model review of my eval harness. I changed the goals to show only the spec, regenerated all the tasks, and re-ran. The number dropped from 79.9 to 67.3. HumanEval never had the leak and didn't move, staying around 80, which is the consistency check you would want to see. The number I report is the lower one, 67.3. For a research talk, I think it counts more that I caught and fixed this in my own setup.

WHAT TO SAY (≈70s): The last thread: can the agent improve its own instructions? Not by retraining; the model weights stay frozen. Instead I tune a text document, a skill, that the agent reads before it works. The loop is along the top: start from a skill, run the agent on training tasks, have a second model propose edits, and keep an edit only if it raises the score on a held-out split. Then I tested three versions once each: an empty skill, a human-written TDD seed, and the optimized one. They came out at 78.6, 73.8, and 77.4 percent. When I re-ran the exact same config, about 6 of 84 tasks flipped just from the model's randomness. So the gaps between the bars are smaller than that run-to-run noise, the yellow brackets. The result is inconclusive and under-powered, and the McNemar p-values are all well above 0.05; I have them if you want them. I measured carefully enough to see it is a wash, instead of reporting the 77 as a win.

Limits, and what's next

  • Toy-to-moderate scale: 67.3% overall, but only 21.6% on hard tasks. Not SWE-bench-grade repo surgery.
  • No real tool parallelism, one shared workspace, and a stochastic open-weight model. The same task can flip run to run.
  • What I learned: most of the reliability came from engineering rather than from the model itself. Writing it myself is what let me find the failure modes.
