Pi khác chúng ta ở chỗ nào?

Một bài học từ ý tưởng xuống tới cách lắp ráp cụ thể: Pi đặt cược vào "harness mỏng, năng lực lắp ngoài"; agent của bạn đi đường khác — local-first, có sandbox, đo trung thực. Hiểu rõ chỗ khác nhau để biết cái gì nên mượn, cái gì phải giữ.

Đọc thế nào Đây là tài liệu học, không phải tài liệu tiếp thị. Mọi con số đều có nguồn (mục 07) hoặc đo trực tiếp từ code của bạn. Khi mình nói "agent của chúng ta", nghĩa là repo coding-agent bạn đang xây — ReAct from-scratch bằng Python, chạy Qwen3-14B local qua vLLM.

Pi = badlogic/pi-mono (Mario Zechner, MIT, TypeScript) · Của chúng ta = Qwen3-14B / vLLM · 2× RTX A6000 · Knox 361

01Pi là gì — triết lý "harness mỏng, năng lực lắp ngoài"

Lõi cực nhỏ. Mọi năng lực thêm vào nằm BÊN NGOÀI lõi, qua Skills / Extensions / Packages.

Pi (repo badlogic/pi-mono của Mario Zechner — cũng là cha đẻ libGDX) là một coding agent open-source, giấy phép MIT, viết bằng TypeScript. Triết lý trung tâm của nó là: cái harness (bộ khung điều khiển vòng lặp agent) nên mỏng đến mức gần như không có gì. Lõi chỉ lo một việc: chạy vòng lặp "model gọi tool → thực thi → đưa kết quả lại cho model". Tất cả những gì không thiết yếu — sandbox, sub-agent, MCP, kỹ năng chuyên biệt — không nằm trong lõi.

Hệ quả của triết lý này rất rõ: muốn Pi làm được nhiều hơn, bạn không sửa lõi — bạn cắm thêm một extension hoặc một skill ở ngoài. Lõi giữ nguyên bé tí, dễ đọc, dễ tin. Đây là kiểu thiết kế "Unix-y": làm một việc và làm tốt, còn lại để ghép.

Ý chính Pi không cố giỏi bằng cách nhồi năng lực vào trong. Nó giỏi bằng cách giữ lõi sạch và đẩy mọi thứ phức tạp ra ngoài rìa — nơi bạn có thể thêm/bớt mà không động vào tim của hệ thống. So với chúng ta: chúng ta nhồi 10 tool vào một registry duy nhất bên trong — đơn giản hơn để bắt đầu, nhưng kém "mở" hơn.

025 trụ cột cụ thể của Pi

Triết lý ở trên biến thành 5 lựa chọn thiết kế rất cụ thể. Đây là phần "cách lắp ráp".

1

4 tool mặc định — mọi thứ khác ủy thác cho bash

Pi chỉ ship 4 tool lõi: read, write, edit, bash. Không có run_python, không multi_edit, không spawn_subagent trong mặc định — vì Pi cố ý không có sub-agent. Cần chạy Python? → bash python .... Cần grep? → bash grep .... Triết lý: shell đã là một "tool vạn năng", nên đừng nhân bản nó thành chục tool riêng.

Điểm tinh tế: tool edit nhận một MẢNG (array) các edit trong một lần gọi — sửa nhiều chỗ trong một file mà không cần một tool multi_edit tách biệt. Một tool, nhiều thao tác.

// edit của Pi: một lời gọi, mảng nhiều thay đổi
{
  "path": "src/app.ts",
  "edits": [
    { "oldText": "const x = 1", "newText": "const x = 2" },
    { "oldText": "foo()",       "newText": "bar()" }
  ]
}
2

System prompt ~400 token — sinh ra theo tool đang bật

Prompt hệ thống của Pi chỉ khoảng ~400 token. Quan trọng hơn cả độ ngắn: nó được sinh động (generated) tùy theo những tool nào đang được bật. Mỗi tool mang theo một dòng mô tả ngắn — gọi là promptSnippet. Khi build prompt, Pi nối các snippet của những tool đang bật lại. Tool nào bị tắt → tốn 0 token trong prompt.

// mỗi tool tự khai báo một dòng prompt của riêng nó
const bashTool = {
  name: "bash",
  promptSnippet: "Use `bash` to run shell commands...",
  // ...
};
// system-prompt.ts nối snippet của các tool ĐANG BẬT → prompt cuối cùng

Đây là một ý đẹp: prompt không phải một khối tĩnh khổng lồ, mà là tổng của các mảnh, chỉ tính phí cho cái đang dùng.

3

models.json — tách model/provider khỏi vòng lặp

Pi không hardcode model trong code logic. Việc "dùng model nào, provider nào, endpoint ở đâu" nằm trong một file dữ liệu (models.json). Đổi model = sửa một file data, không sửa code. Vì endpoint là OpenAI-compatible nên cũng chính cơ chế đó cho phép trỏ vào Ollama, LM Studio, hay vLLM local.

// ~/.pi/agent/models.json — đổi model là đổi data, không phải code
{
  "models": [
    { "id": "my-local", "provider": "openai-compatible",
      "baseUrl": "http://localhost:8000/v1", "model": "Qwen3-14B" }
  ]
}
4

Không sandbox ("YOLO") — cô lập đẩy ra NGOÀI process

Pi không có sandbox bên trong tool layer. Một lệnh bash chạy thẳng. Triết lý: an toàn không phải việc của agent harness — nếu bạn cần cô lập, hãy bọc cả tiến trình Pi trong một container hoặc một phiên tmux. Cô lập là một tầng bên ngoài, không nhét vào trong từng tool.

Hệ quả: lõi đơn giản hơn (không có code kiểm tra đường dẫn), nhưng đặt trách nhiệm an toàn lên người chạy. Đây chính là chỗ agent của chúng ta đi ngược lại — xem trụ cột tương ứng ở mục 03.

5

Một "session object" — phiên là cây JSONL (fork / branch / clone)

Vòng lặp của Pi xoay quanh một đối tượng session duy nhất. Lịch sử hội thoại được lưu thành cây JSONL: bạn có thể fork một phiên, branch ra hướng khác, hay clone để thử nghiệm — mà không phá nhánh gốc. Khi context dài quá, Pi compaction (nén lại) để vừa cửa sổ ngữ cảnh. Tất cả gói trong một vòng lặp, không có vòng lặp song song hay sub-agent thứ hai.

Tóm lại 5 trụ cột 4 tool (mọi thứ khác → bash; edit nhận mảng; không sub-agent) · prompt ~400 token sinh động theo tool · models.json tách model khỏi code · không sandbox (cô lập ở ngoài) · một session = cây JSONL có fork/branch + compaction.

03Agent của chúng ta — đường đi khác

ReAct from-scratch bằng Python, chạy model local, có rào an toàn trong process, và đo bằng eval thật.

Agent của bạn cũng theo tinh thần tối giản, nhưng các lựa chọn cụ thể khác Pi ở nhiều chỗ — và mỗi chỗ khác đều có lý do:

Model local: Qwen3-14B qua vLLM

Không "bring-your-own cloud key" như Pi. Agent của bạn chạy Qwen3-14B local trên 2× A6000 — minh bạch hoàn toàn, không phụ thuộc API ngoài, và là sân để fine-tune sau này.

10 tool trong một registry

read_file, write_file, run_bash, apply_patch, multi_edit, grep_files, glob_files, list_dir, run_python, spawn_subagent — tất cả trong TOOLS / TOOL_SCHEMAS. Nhiều hơn Pi gấp 2.5×, vì chúng ta cho model nhỏ những tool chuyên biệt rõ ràng thay vì dồn hết vào bash.

_safe_path — sandbox trong process

Mỗi tool đụng file đều đi qua _safe_path() — chặn path-traversal (CWE-22): không cho thoát khỏi workspace bằng ../../. Đây là rào an toàn nằm bên trong tool layer — ngược hẳn với "YOLO" của Pi.

Prompt ~1K token, viết tay

System prompt của chúng ta (SYSTEM_PROMPT trong prompts.py) là một khối viết tay ~1K token (đo được ~862 token theo char-count), không sinh động theo tool như Pi.

Pi không công bố con số eval nào. Agent của bạn được đo trung thực trên 627 task với hidden test: 79.9% (501/627), lên ~92% khi model thực sự chịu gọi tool. Khoảng cách đó chính là phát hiện no_action — 84 ca model trả lời prose mà không gọi tool nào. Đây là một phát hiện empirical của riêng bạn.

Hai điểm cần thành thật về code hiện tại

⚠️ Nợ kỹ thuật #1 — hai vòng lặp ReAct trùng nhau Hiện có HAI vòng lặp ReAct riêng biệt: run_agent() trong src/agent.py (dùng cho eval/solve) và vòng lặp tương tác trong cli/chat.py (chat() + stream_one_turn()). Chúng làm gần như cùng một việc nhưng là hai bản code song song → dễ lệch nhau. Pi chỉ có một vòng lặp session.
⚠️ Nợ kỹ thuật #2 — guardrail no_action chỉ có ở một loop Việc phát hiện và xử lý no_action chỉ tồn tại trong agent.py (xem dòng ~689–693). Vòng lặp chat.py không có nó. Nghĩa là chính cái guardrail giá trị nhất của bạn lại không được dùng nhất quán ở cả hai chỗ — một lý do nữa để gộp hai loop làm một.

05Bài học: BORROW / KEEP / DECLINE

Không phải cái gì của Pi cũng nên copy. Chia làm ba nhóm rõ ràng.

↓ BORROW — mượn từ Pi

  • Gộp 2 loop → 1. Một vòng lặp session duy nhất, dùng chung cho cả eval lẫn chat. Hết cảnh hai bản code lệch nhau; no_action guardrail tự động có mặt ở mọi nơi.
  • Thu gọn tool 10 → ~5. Để edit hấp thụ apply_patch + multi_edit (mảng edit như Pi); gập run_python vào bash; đặt cổng (gate) cho spawn_subagent.
  • models.json. Tách model/provider khỏi code; bỏ max_tokens=2048 hardcode ra file data.
  • Snippet-per-tool prompt. Mỗi tool mang một dòng promptSnippet; prompt sinh động theo tool đang bật → tool tắt tốn 0 token.

= KEEP — giữ lợi thế của mình

  • _safe_path sandbox. Đừng "Pi hoá" thành YOLO. Rào CWE-22 trong process là điểm hơn — giữ.
  • Local-first Qwen3-14B. Đây là cả lý do tồn tại của dự án; minh bạch + sân fine-tune.
  • Eval 627 task trung thực. Thứ Pi không có. Giữ làm tín hiệu thật, đừng đánh đổi lấy "đẹp".
  • Guardrail no_action. Phát hiện empirical của riêng bạn — giữ và nhân rộng ra cả loop hợp nhất.

✕ DECLINE — không mượn

  • Extension bus 25 event. Sẽ làm chúng ta phức tạp hơn, không đơn giản hơn. Một registry là đủ cho quy mô một người.
  • No-sandbox / YOLO. Đi ngược điểm mạnh; bỏ _safe_path là tự bắn vào chân.
  • Multi-provider registry. Chúng ta chạy một model local. Hạ tầng đa-provider là gánh nặng không dùng tới.
Nguyên tắc lọc Mượn thứ làm code đơn giản hơn và nhất quán hơn (gộp loop, gọn tool, models.json, snippet prompt). Từ chối thứ chỉ "giống Pi" nhưng làm ta phức tạp hơn (event bus, đa provider) hoặc yếu đi (bỏ sandbox).

06Sự thật quan trọng — code của bạn KHÔNG phình

Trước khi nghĩ tới "viết lại cho gọn như Pi": hãy nhìn con số thật. "To" ở đây phần lớn là chú thích dạy học, không phải logic thừa.

Đo trực tiếp trên repo của bạn hôm nay:

Tương tự, vòng lặp ReAct trong run_agent() trải dài ~470 dòng văn bản, nhưng phần lớn là chú thích: chỉ khoảng ~90–195 dòng code thực (đo strict không-chú-thích-không-trống ≈ 93 dòng). Nói cách khác:

Kết luận thành thật File tools.py "to" không phải vì logic rối — mà vì có ~540 dòng chú thích tiếng Việt cố ý để dạy. Bỏ chú thích ra, logic chỉ ~300–350 dòng; vòng lặp ReAct chỉ ~90–195 dòng code thật. Cho nên "gọn như Pi" KHÔNG cần một cuộc viết lại — nó là vài nước đi nhắm đích: gộp 2 loop, gọn 10 tool xuống ~5, đẩy config ra models.json, prompt theo snippet. Đừng đập đi xây lại; chỉ cần tỉa đúng chỗ.

(Con số đo bằng wc -l + đếm dòng chú thích/trống trên repo ngày 2026-05-26; logic "thực" là ước lượng sau khi trừ comment và blank.)
