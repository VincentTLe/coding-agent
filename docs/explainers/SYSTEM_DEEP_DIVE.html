Coding Agent, hiểu từ số 0

Một AI coding agent viết tay từ con số 0 — không framework — điều khiển Qwen3-14B chạy local để đọc, sửa, chạy và tự kiểm chứng code.

Tài liệu này đi từ dễ tới khó: khái niệm trước, rồi xem nó chạy thật, rồi mới mở từng lớp code. Mỗi mục bắt đầu bằng một sơ đồ và một ý; chi tiết nặng được gập lại sau nút ▸ đi sâu để bạn không bị ngợp.

📖 Cách đọc: cuộn từ trên xuống theo thứ tự 01 → 06. Đọc phần hiện sẵn là đã nắm ý chính; chỉ mở "đi sâu" khi tò mò muốn xem từng dòng. Không cần mở hết.

Chương 1 · Nền tảng DỄ

01Một LLM thực sự làm gì

Bỏ hết hào nhoáng "AI": lõi của mọi thứ chỉ là một bộ đoán chữ. Hiểu 4 ý nhỏ ở đây là đủ nền cho toàn bộ phần còn lại.

1LLM = bộ đoán token kế tiếp

Cho một chuỗi chữ, model tính xác suất cho token (mẩu chữ) tiếp theo, chọn một mẩu, nối vào, rồi lặp lại. Nó không "hiểu" — nó đoán. Cứ đoán-nối-đoán-nối là thành câu.

Ý chính Sinh văn bản = lặp "đoán 1 token → nối vào → đoán tiếp". Vòng lặp nhỏ này, nâng lên một bậc, chính là vòng lặp của agent ở Chương 2.

2Danh sách messages chính là bộ nhớ

Server LLM không nhớ gì giữa các lần gọi (nó stateless). Muốn nó "nhớ" hội thoại, mỗi lượt ta phải gửi lại toàn bộ lịch sử. "Trí nhớ" của agent không nằm trên server — nó là một list trong code của ta, ta tự bồi đắp qua từng lượt.

Bất biến cốt lõi Danh sách messages CHÍNH LÀ bộ nhớ. Model thì stateless; toàn bộ "agent" sống trong vòng lặp giữ và gửi lại list này mỗi lượt. Nhớ ý này — nó quay lại ở mọi chương sau.

3Bốn vai (role) trong cuộc hội thoại

Mỗi phần tử trong messages có một role. Chỉ cần nhớ 4 vai:

messages = [
  {"role": "system",    "content": "Bạn là coding agent..."},   # luật chơi
  {"role": "user",      "content": "Sửa test đang fail"},        # yêu cầu
  {"role": "assistant", "content": "Để tôi xem repo đã",         # model nói / hành động
                        "tool_calls": [{"id": "call_1", "...": "..."}]},
  {"role": "tool",      "tool_call_id": "call_1",                # KẾT QUẢ của call_1
                        "content": "calculator.py\ntest_calculator.py"},
]
Quy tắc ghép cặp (nhớ một lần, dùng mãi) Mỗi assistant có tool_calls phải được theo sau bởi đúng một message tool cho mỗi tool_call_id. Lệch cặp này → API trả lỗi 400 và hỏng cả run. Mọi đoạn code "rắc rối" ở chương sau thực ra chỉ để giữ đúng cặp này.

4Chatbot chỉ biết nói; agent biết làm

Chatbot sinh ra chữ rồi dừng. Một agent chạy một vòng lặp: Reason (nghĩ) → Act (gọi một tool: đọc/sửa file, chạy test) → Observe (đọc kết quả) → nghĩ tiếp. Mẫu này tên là ReAct. Vòng lặp dừng khi model trả lời mà không gọi tool nào nữa — đó là tín hiệu "tôi xong rồi".

Ý chính Chatbot = một lần hỏi-đáp. Agent = một vòng lặp nghĩ→làm→nhìn. Chính vòng lặp này biến một model "chỉ biết nói" thành thứ làm được việc.
Đi sâu: context window 32K & temperature

Context window = số token tối đa model "nhìn" được một lúc (ở đây 32K, cố định khi train vì chi phí attention là O(n²)). Lịch sử hội thoại cứ phình ra theo từng tool call → có lúc đụng trần 32K → đây chính là lý do Chương 5 phải có compaction (tóm tắt lịch sử cũ).

Temperature = núm xoay độ ngẫu nhiên khi chọn token. Cao (~1.0) = sáng tạo/ngẫu nhiên; thấp (0.0) = bám token chắc ăn nhất, ổn định. Khi đo điểm (eval) ta đặt temperature=0.0 để kết quả tái lập được; đây cũng là một mẹo giảm lỗi "nói mà không làm" ở Chương 6.

✓ Đã hiểu tới đây
  • LLM = vòng lặp đoán token; messages là bộ nhớ ta tự giữ.
  • 4 vai: system / user / assistant / tool — và quy tắc ghép cặp tool_call_id.
  • Agent = vòng lặp ReAct, dừng khi không còn tool_calls.

Tiếp theo → thay vì định nghĩa thêm, ta xem chính vòng lặp đó chạy thật trên một bug có thật.

Chương 2 · Xem nó chạy DỄ

02Một lượt chạy thật, kể đơn giản

Trước khi mở bất kỳ dòng code nào, hãy xem agent sửa một bug thật. Đây là "sợi chỉ đỏ" — ta sẽ quay lại đúng lượt chạy này ở các chương sau.

🐞 Bug thật trong demo_repo/calculator.py

def add(a: int, b: int) -> int:
    # BUG: trả a - b thay vì a + b
    return a - b

Nhiệm vụ giao cho agent: "Fix the failing tests in demo_repo/". Test assert add(2, 3) == 5 đang fail vì 2 − 3 = −1.

Agent chạy đúng vòng ReAct ở Chương 1. Mỗi lượt nó gọi một tool; ta chạy tool, nối kết quả vào messages, rồi để nó nghĩ tiếp:

Turn 1 · Act nhìn xem repo có gì
list_dir(".") messages += assistant(tool_calls=[list_dir]) , tool("calculator.py, test_calculator.py, ...")
Turn 2 · Act chạy test để thấy lỗi
run_bash("pytest -x") tool("test_add_positive FAILED — assert add(2,3)==5, nhận -1")
Turn 3 · Reason+Act đọc file để tìm bug
read_file("calculator.py") tool("...return a - b # BUG...")
Turn 4 · Act sửa đúng một chỗ
apply_patch("calculator.py", old="return a - b", new="return a + b") tool("patched calculator.py: replaced 12 chars with 12 chars")
Turn 5 · Act chạy lại test để tự kiểm chứng
run_bash("pytest") tool("3 passed in 0.01s")
Turn 6 · DONE trả lời, KHÔNG gọi tool nữa
"Đã sửa add thành a + b; cả 3 test pass." → không có tool_calls → vòng lặp dừng.
Đây chính là toàn bộ hệ thống Mọi thứ còn lại của tài liệu chỉ là phóng to 6 lượt này: các tool (Ch3), vòng lặp điều phối chúng (Ch4), hạ tầng chạy model (Ch5), và cách đo xem nó làm đúng bao nhiêu phần trăm (Ch6).
Đi sâu: vì sao "tự chạy lại pytest" là điểm mấu chốt

Turn 5 là thứ phân biệt một agent thật với một chatbot. Sau khi sửa, agent tự chạy lại test và đọc kết quả — nếu vẫn fail, nó lặp tiếp ở Turn 7, 8... Nó không "tin" là mình đã sửa đúng; nó kiểm chứng bằng feedback có thật từ pytest. System prompt (Ch3) ép đúng quy trình này: list_dir → pytest -x → read → apply_patch → pytest → done.

File demo_repo/algorithms.py có phiên bản khó hơn: 2 bug (trong is_prime và factorial) — cùng một vòng lặp, chỉ là nhiều turn hơn.

✓ Đã hiểu tới đây
  • Bạn vừa thấy vòng ReAct ở Ch1 chạy thật: mỗi turn một tool, kết quả nối lại vào messages.
  • Agent tự verify bằng pytest, lặp tới khi xanh, rồi dừng bằng cách thôi gọi tool.

Tiếp theo → mở lớp đầu tiên: các tool đó thực ra là gì, và làm sao chúng an toàn.

03Các tool: model "đòi", ta "làm"

Model không tự đụng được vào máy. Nó chỉ đề nghị gọi tool; code của ta mới thực thi — và đó là nơi đặt mọi lớp an toàn.

1Hợp đồng: schema vào, tool_calls ra

Ta mô tả mỗi tool bằng một JSON schema để model biết tool tên gì, nhận tham số nào. Model đọc schema, rồi "đòi" gọi tool bằng cách trả về tool_calls (tên + arguments là một chuỗi JSON, không phải dict).

# Một schema (model ĐỌC cái này) — đây là tool read_file:
{"type": "function",
 "function": {
   "name": "read_file",
   "description": "Read the full contents of a text file (path relative to workspace).",
   "parameters": {"type": "object",
     "properties": {"path": {"type": "string", "description": "Relative path to the file."}},
     "required": ["path"]}}}
Ý chính Schema là "thực đơn" model nhìn vào. Cùng một định dạng schema này chạy được với GPT-4, Claude, vLLM, Ollama — đổi backend không phải đổi tool.

3Nhìn gần một tool: apply_patch

Đây là tool sửa code chính (tránh ghi đè cả file). Toàn bộ "trí khôn" của nó là một quy tắc: old_text phải khớp đúng một lần.

count = content.count(old_text)
if count == 0:                      # không thấy → model nhớ sai bytes
    return "ERROR: old_text not found... Read the file to get exact bytes."
if count > 1:                       # mơ hồ → biết thay chỗ nào?
    return "ERROR: old_text matches N places... add more context."
new_content = content.replace(old_text, new_text, 1)   # đúng 1 chỗ → thay
p.write_text(new_content)
Ý chính "Khớp đúng một lần" vừa là safety (không thay nhầm chỗ), vừa là feedback: nếu lỗi, message chỉ rõ model phải làm gì (đọc lại file / thêm ngữ cảnh) thay vì thất bại im lặng.

4Ổ khoá: _safe_path nhốt agent trong sandbox

Mọi thao tác file đều đi qua hàm này trước. Nó ghép đường dẫn, resolve tuyệt đối, rồi từ chối nếu kết quả nằm ngoài workspace:

def _safe_path(path, workspace):
    p = (workspace / path).resolve()
    if workspace not in p.parents and p != workspace:
        raise ValueError(f"path {p} escapes workspace {workspace}")
    return p

5Bộ điều phối execute_tool + hợp đồng "lỗi là chuỗi"

Một hàm duy nhất nhận tên tool + chuỗi JSON, parse, tra hàm, gọi, và bắt mọi exception biến thành chuỗi "ERROR: ..." — không bao giờ raise lên vòng lặp.

def execute_tool(name, arguments, workspace):
    if name not in TOOLS:
        return f"ERROR: unknown tool {name}..."
    args = json.loads(arguments) if arguments else {}
    try:
        result = TOOLS[name](**args, workspace=workspace)   # inject workspace
    except TypeError as e:
        return f"ERROR: bad args for {name}: {e}"
    except Exception as e:
        return f"ERROR: {name} crashed: {e}"
    return result
Bất biến: lỗi không bao giờ làm sập agent Một tool hỏng KHÔNG ném exception giết cả run — nó trả một chuỗi "ERROR: ...". Model đọc chuỗi đó ở turn sau và tự sửa. Đây là điều biến lỗi thành feedback thay vì crash.
Đi sâu: vì sao model không bao giờ thấy workspace

workspace cố tình không có trong TOOL_SCHEMAS — model không biết, không gửi. execute_tool tự tiêm workspace=workspace vào mỗi lời gọi (keyword-only). Đó là state của caller, không phải thứ model được quyết. Nhờ vậy mỗi agent (kể cả subagent) chạy với sandbox riêng mà không có biến global chung — an toàn khi chạy song song.

Một bất biến nữa, kiểm ngay lúc import: assert set(TOOLS) == {tên trong TOOL_SCHEMAS}. Thêm tool mà quên schema (hoặc lệch tên) → fail ngay khi import, không phải lỗi mơ hồ lúc chạy.

✓ Đã hiểu tới đây
  • Model chỉ đề nghị qua tool_calls; code ta thực thi 10 tool (4 nhóm).
  • _safe_path nhốt mọi thao tác file trong sandbox; execute_tool biến mọi lỗi thành chuỗi để agent tự sửa.

Tiếp theo → ai gọi execute_tool, và lặp lại bao nhiêu lần? Đó là vòng lặp ở Chương 4.

Chương 4 · Bên trong vòng lặp VỪA

04run_agent: trái tim 12 dòng

Bỏ hết comment và xử lý lỗi, vòng lặp ReAct ở Chương 2 thu lại còn khoảng một tá dòng. Đây là toàn bộ "động cơ".

1Vòng lặp lõi

messages = [{"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": goal}]

for i in range(1, max_iters + 1):
    resp = client.chat.completions.create(
        model=model, messages=messages,
        tools=TOOL_SCHEMAS, tool_choice="auto")     # cho model TỰ quyết gọi tool
    msg = resp.choices[0].message
    messages.append(msg.model_dump(exclude_none=True))   # giữ NGUYÊN tool_calls

    if not msg.tool_calls:        # model thôi gọi tool → coi như xong
        return {"finish_reason": "finished", "iters_used": i}

    for tc in msg.tool_calls:     # chạy từng tool, nối kết quả vào messages
        result = execute_tool(tc.function.name, tc.function.arguments, workspace)
        messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})
Khớp với Chương 2 So lại 6 turn của bug calculator: mỗi vòng for là một turn. create() = Reason, execute_tool = Act, append(role:"tool") = Observe. Hết tool_calls = Turn 6 (DONE).
Vì sao model_dump(exclude_none=True) Phải append nguyên message của model (không tự dựng lại bằng tay) để giữ mảng tool_calls. Mất nó là phá đúng quy tắc ghép cặp ở Chương 1 → API trả 400. exclude_none chỉ rụng field rỗng, không đụng tool_calls.

2Lan can no_action: "nói mà không làm"

Có một lỗ hổng tinh vi: đôi khi model trả lời bằng văn xuôi (mô tả cách sửa, thậm chí viết code dạng text) mà không gọi tool nào ngay turn đầu. Vòng lặp ngây thơ sẽ thấy "hết tool_calls" và tưởng xong — nhưng đĩa chưa đổi gì, task fail oan.

Cách chặn: nhớ agent đã thực sự làm việc chưa (made_tool_call). Nếu chưa mà đã "xong" → nhắc nó (tối đa 2 lần), không được nữa thì đánh dấu riêng no_action (khác hẳn "finished" thật):

if not msg.tool_calls:
    if made_tool_call:                                  # đã làm thật → tin là xong
        return {"finish_reason": "finished", "iters_used": i}
    if nudges_used < MAX_NUDGES and i < max_iters:       # chưa làm gì → nhắc
        nudges_used += 1
        messages.append({"role": "user", "content": NUDGE})
        continue
    return {"finish_reason": "no_action", "iters_used": i}   # nói mà không làm
Giữ lại để đo no_action không chỉ là cái sửa — nó là một nhãn. Nhờ tách nhãn này, ở Chương 6 ta đo được CHÍNH XÁC bao nhiêu task thất bại kiểu "nói mà không làm" (84 task) — đó là phát hiện riêng của dự án.
Đi sâu: 5 cách kết thúc & ca biên turn cuối

run_agent luôn trả về một trong 5 finish_reason: finished (xong thật), no_action (nói mà không làm), max_iters (hết lượt vẫn đòi gọi tool), api_error (vLLM rớt/timeout/context tràn — bắt OpenAIError để 1 lỗi không giết cả run), timeout (vượt ngân sách wall-clock của eval).

Điều kiện i < max_iters trong nudge là một ca biên thật: nếu đang ở turn cuối thì nhắc cũng vô nghĩa (model không kịp đáp) → rơi thẳng xuống no_action. Tương tự, nếu turn cuối model vẫn đòi gọi tool, ta KHÔNG chạy (kết quả sẽ không bao giờ được model đọc lại, mà có thể đã ghi đĩa) → dừng và báo max_iters. iters_used luôn là i (1-based) ở mọi nhánh để eval đếm nhất quán.

✓ Đã hiểu tới đây
  • Cả agent gói trong ~12 dòng: gọi model → append (giữ tool_calls) → hết tool thì dừng → ngược lại chạy tool, nối kết quả, lặp.
  • Lan can no_action chặn lỗi "nói mà không làm" và gắn nhãn để đo được sau.

Tiếp theo → tới phần khó hơn: cái gì chạy model này, và làm sao sống sót qua hội thoại dài.

2REPL streaming: chữ chảy real-time

Bản REPL (giống Claude Code) bật stream=True để hiện token ngay khi model sinh, thay vì chờ cả câu. Mỗi chunk mang một mẩu; ta phân loại và ghép lại:

stream = client.chat.completions.create(..., stream=True,
    extra_body={"chat_template_kwargs": {"enable_thinking": thinking_enabled}})
for chunk in stream:
    delta = chunk.choices[0].delta
    if delta.reasoning_content:  ...   # phần "nghĩ" — in xám
    if delta.content:            ...   # câu trả lời — in màu
    if delta.tool_calls:         ...   # GHÉP lại: id / name / arguments đến rời rạc
Ý chính tool_calls khi streaming về thành nhiều mảnh (tên ở chunk đầu, JSON arguments rải qua nhiều chunk) — phải tự tích luỹ theo index rồi mới chạy. Nút /think bật/tắt suy nghĩ chỉ là lật cờ enable_thinking này.
Đi sâu: ghép tool_calls từ các mảnh stream (code thật)

Mỗi chunk mang một mẩu của tool call; ta nối chuỗi (+=) vào đúng slot theo index (hỗ trợ nhiều tool song song), cuối stream mới có call hoàn chỉnh để chạy:

if delta.tool_calls:
    for tcd in delta.tool_calls:          # mỗi chunk = một mẩu
        idx = tcd.index
        if idx not in tool_calls:
            tool_calls[idx] = {"id": "", "name": "", "arguments": ""}
        if tcd.id:
            tool_calls[idx]["id"] += tcd.id
        if tcd.function:
            if tcd.function.name:
                tool_calls[idx]["name"] += tcd.function.name
            if tcd.function.arguments:    # JSON args rải qua NHIỀU chunk
                tool_calls[idx]["arguments"] += tcd.function.arguments

Trái với src/agent.py (không stream) chỉ cần resp.choices[0].message.tool_calls đã đầy đủ — REPL phải tự "khâu" lại vì đó là cái giá của việc hiện chữ real-time.

3Sống sót hội thoại dài: compaction

Mỗi turn nhồi thêm message; qua 20–30 turn dễ vượt trần 32K (Chương 1) → vLLM trả 400, REPL chết. Lời giải (mượn của Claude Code): khi gần đầy, tóm tắt phần cũ thành một message, giữ nguyên các turn gần nhất.

[system, m1, m2, … m25]~đầy 32K
→
[system, summary, m16…m25]gọn lại
COMPACT_THRESHOLD_TOKENS = 24000   # kích hoạt ở ~75% của 32K (chừa headroom)
KEEP_RECENT_MESSAGES     = 10      # giữ 10 message cuối NGUYÊN VĂN
# ước lượng token ≈ tổng_ký_tự // 4  (đủ tốt để quyết định, không cần exact)
Cạm bẫy điểm cắt Chỗ cắt giữa "tóm tắt" và "giữ lại" bắt buộc rơi vào một message role:"user" (ranh giới turn sạch). Cắt nhầm vào giữa cặp assistant.tool_calls → tool sẽ để lại tool "mồ côi" → API 400. Lại đúng quy tắc ghép cặp ở Chương 1 — nó theo ta tới tận đây.
Đi sâu: vì sao ước lượng token thô (chars/4) là đủ

Không dùng tokenizer thật (tiktoken sai cho Qwen3; HuggingFace cần load ~50MB). Ta chỉ cần biết "đã gần trần chưa?" chứ không cần con số chính xác — sai số 20–30% vẫn ổn vì ngưỡng 24K đã chừa đệm cho cả response (~2K) lẫn sai số. Đổi lại: zero phụ thuộc, zero startup cost. Đây là một đánh đổi kỹ thuật điển hình: chọn "đủ tốt + rẻ" thay vì "hoàn hảo + đắt".

Đi sâu: tìm điểm cắt an toàn (code thật)

Để không bỏ một tool "mồ côi", điểm cắt phải đi tới trước từ vị trí -KEEP_RECENT cho tới khi gặp một message role:"user" — một ranh giới turn sạch:

split = len(messages) - KEEP_RECENT_MESSAGES
while split < len(messages) and messages[split]["role"] != "user":
    split += 1                       # đi TỚI TRƯỚC tới khi gặp user
to_summarize = messages[1:split]     # phần cũ → nén thành 1 summary
recent       = messages[split:]      # giữ nguyên (bắt đầu từ user → sạch)

Vì recent luôn bắt đầu tại một user message, mọi tool trong đó chắc chắn có assistant.tool_calls của nó đứng trước (cùng trong recent) → không bao giờ mồ côi. Đi tới trước (không lùi) chỉ làm recent ngắn lại → an toàn cho ngân sách context.

multi_edit: sửa nhiều chỗ kiểu "tất cả hoặc không gì"

Đọc file một lần vào RAM → áp tuần tự từng edit lên biến chuỗi → ghi một lần. Nếu bất kỳ edit nào trượt kiểm "khớp đúng một lần", trả lỗi trước khi ghi → file gốc trên đĩa không bị động. Tránh tình trạng file bị sửa dở (partial edit) không cứu được.

content = p.read_text(...)                 # đọc ĐÚNG một lần vào RAM
for i, edit in enumerate(edits, 1):        # áp tuần tự — vẫn TRONG RAM
    count = content.count(edit["old_text"])
    if count != 1:                         # 0 hoặc >1 → trả lỗi, CHƯA ghi gì
        return f"ERROR: edit #{i}: ... (file not modified)"
    content = content.replace(edit["old_text"], edit["new_text"], 1)
p.write_text(content)                      # mọi edit pass → ghi ĐÚNG một lần
spawn_subagent: chia để trị bằng tiến trình con

Đẻ một agent con bằng subprocess riêng (không đệ quy in-process): cô lập messages, không phình context cha, không lo stack overflow, crash con không giết cha, và giết theo timeout 300s là một lời gọi. Nó tự "đi lên" cây thư mục để tìm project root (nơi có src/agent.py), trả về 2000 ký tự cuối của output con.

# 1) đi ngược lên (tối đa 10 cấp) tìm project root chứa src/agent.py
# 2) chạy agent con trong MỘT process riêng:
result = subprocess.run(
    [sys.executable, "-m", "src.agent", goal, "--workspace", str(workspace)],
    cwd=project_root, capture_output=True, text=True, timeout=300)
# 3) trả 2000 ký tự CUỐI (câu trả lời + "Agent finished." nằm ở cuối log)

run_bash: chạy shell, gói trọn exit/stdout/stderr

Cửa ra shell cho pytest/git/pip. Tham số tên là command (không phải cmd); chạy ngay trong sandbox và gói kết quả thành một chuỗi để model đọc:

def run_bash(command: str, timeout: int = 600, *, workspace: Path) -> str:
    try:
        r = subprocess.run(command, shell=True, cwd=workspace,   # CWD = sandbox
                           capture_output=True, text=True, timeout=timeout)
    except subprocess.TimeoutExpired:
        return f"ERROR: command timed out after {timeout}s"      # trả chuỗi, KHÔNG raise
    return f"exit_code: {r.returncode}\nstdout:\n{r.stdout}\nstderr:\n{r.stderr}"

run_python dùng đúng khuôn output này (timeout 60s) để model chỉ phải học một kiểu kết quả.
